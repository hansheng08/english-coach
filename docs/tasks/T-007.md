### 1. `supabase/functions/_shared/db/client.ts`（新增）
資料庫存取基礎：supabase-js 最小介面 `DbClient`、`runDb`（把例外與 `{ error }` 轉成 `Result`）、以使用者身分建立 client（TechLead 決定 1～3）。
```ts
import { err, ok, tryCatchAsync, type AppError, type Result } from '@english-coach/contracts';
import { createClient } from '@supabase/supabase-js';
import type { SupabaseEnv } from '../config/env.ts';
import type { AuthContext } from './auth.ts';

/** supabase-js 回應中 repository 會讀的部分；只在 _shared/db 內使用，不傳出（ADR-008 修訂 1）。 */
export type DbResponse<T> = {
  readonly data: T;
  readonly error: { readonly code?: string | undefined; readonly message: string } | null;
};

/** repository 用到的 supabase-js 最小介面：正式是 createUserClient 的結果，測試給假的。 */
export interface DbClient {
  from(table: string): { insert(row: Readonly<Record<string, unknown>>): PromiseLike<DbResponse<unknown>> };
}

/** 以使用者身分、受 RLS 限制的 client（ADR-010 決定 3：publishable 金鑰＋該使用者的 token）。 */
export function createUserClient(ctx: AuthContext, env: SupabaseEnv): DbClient {
  return createClient(env.url, env.publishableKey, {
    auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
    global: { headers: { Authorization: `Bearer ${ctx.accessToken}` } },
  });
}

/** 把會丟例外或回 `{ error }` 的 supabase-js 呼叫轉成 Result；訊息只有操作名稱與 Postgres 錯誤碼，不含資料（NFR-04）。 */
export async function runDb<T>(op: string, call: () => PromiseLike<DbResponse<T>>): Promise<Result<T, AppError>> {
  const res = await tryCatchAsync(
    async () => await call(),
    (): AppError => ({ kind: 'db_failed', message: `${op} failed` }),
  );
  if (!res.ok) return err(res.error);
  const { data, error } = res.value;
  if (error !== null) {
    return err({ kind: 'db_failed', message: error.code === undefined ? `${op} failed` : `${op} failed (${error.code})` });
  }
  return ok(data);
}
```

### 2. `supabase/functions/_shared/db/provider-call.ts`（新增）
`provider_call` 寫入：只挑 8 個中繼資料欄位，不展開輸入（TechLead 決定 4、5）。
```ts
import {
  ok,
  type AppError,
  type Capability,
  type ProviderErrorKind,
  type ProviderId,
  type Result,
  type Tier,
  type UserId,
} from '@english-coach/contracts';
import { runDb, type DbClient } from './client.ts';

/** 一次外部呼叫的紀錄：只有中繼資料，不含任何使用者文字、錄音或模型輸出（ARCHITECTURE §4、§13；CLAUDE.md）。 */
export type ProviderCallRecord = {
  readonly capability: Capability;
  readonly provider: ProviderId;
  readonly model: string | null;
  readonly tier: Tier;
  /** null＝成功；否則是失敗的種類。 */
  readonly errorKind: ProviderErrorKind | null;
  readonly latencyMs: number;
};

/** 寫入的欄位，必須和 T-006 migration 給 authenticated 的 `grant insert (…)` 一致（tooling/db-provider-call.test.ts）。 */
export const PROVIDER_CALL_COLUMNS = [
  'user_id',
  'capability',
  'provider',
  'model',
  'tier',
  'status',
  'error_kind',
  'latency_ms',
] as const;

export type ProviderCallRow = { readonly [K in (typeof PROVIDER_CALL_COLUMNS)[number]]: string | number | null };

/** 逐欄挑出，不展開 record：record 多帶的任何欄位都不會寫進資料庫。 */
export function providerCallRow(userId: UserId, r: ProviderCallRecord): ProviderCallRow {
  return {
    user_id: userId,
    capability: r.capability,
    provider: r.provider,
    model: r.model,
    tier: r.tier,
    status: r.errorKind === null ? 'ok' : 'error',
    error_kind: r.errorKind,
    latency_ms: Number.isFinite(r.latencyMs) ? Math.max(0, Math.round(r.latencyMs)) : 0,
  };
}

export async function insertProviderCall(
  client: DbClient,
  userId: UserId,
  r: ProviderCallRecord,
): Promise<Result<null, AppError>> {
  const res = await runDb('insert provider_call', () => client.from('provider_call').insert(providerCallRow(userId, r)));
  if (!res.ok) return res;
  return ok(null);
}
```

  return userDbFrom(createUserClient(ctx, env), ctx.userId);
}

## TechLead 決定（ARCHITECTURE／ADR 沒有寫死的實作細節；照做，不需要再問）
1. **三個正式檔、單向依賴**：`client.ts`（基礎：`DbClient`、`DbResponse`、`runDb`、`createUserClient`）← `provider-call.ts`（一張表一個檔）← `user-db.ts`（對 endpoint 的入口）。`createUserDb` 放在 `user-db.ts` 而不是 `client.ts`，是為了避免 `client.ts` ↔ `provider-call.ts` 循環（ADR-008 第 10 條）。之後新增的表照同樣做法：新增 `<表>.ts`，在 `UserDb` 加一個回 `Result` 的函式。
2. **`DbClient` 是本專案自己的最小介面**（只有 `from(table).insert(row)`），不是 `SupabaseClient`；`createUserClient` 回傳 supabase-js client 時由 `tsc` 證明它符合這個介面（`pnpm check` 的 typecheck）。endpoint 只拿到 `UserDb`（裡面只有回 `Result` 的函式，沒有 client、沒有 `{ data, error }`），符合 ADR-008 修訂 1 第 4 條；測試用假的 `DbClient`，不需要網路與資料庫。
3. **`runDb` 的錯誤對應**：supabase-js 丟例外（網路錯誤等）→ `db_failed`／`<操作> failed`；回 `{ error }` → `db_failed`／`<操作> failed (<Postgres 錯誤碼>)`。**不放** PostgREST 的 `message`／`details`（可能含列的內容，NFR-04、§13）；不新增 `AppError` 種類（CLAUDE.md）。
4. **`ProviderCallRecord`**：`capability`、`provider`（`ProviderId`）、`model`（`string | null`）、`tier`、`errorKind`（`ProviderErrorKind | null`，null＝成功）、`latencyMs`。`status` 由 `errorKind` 推出（null → `ok`，否則 `error`），所以一定滿足 T-006 的 `provider_call_error_status_check`；`latency_ms` 四捨五入成整數、負數變 0、非有限數變 0（滿足 `provider_call_latency_ms_check`）；`user_id` 一律取自 `AuthContext`，呼叫端不能指定。
5. **不存內容靠「逐欄挑出」**：`providerCallRow` 逐一寫出 8 個欄位，不用 `...record` 展開，所以呼叫端多帶的任何欄位（例如提示詞、逐字稿）都不會寫進資料庫；資料庫端另有 T-006 的欄位權限與「沒有內容欄位」pgTAP 擋住（AC-T6-1、AC-T6-2）。
6. **`createUserDb(ctx, env)` 不寫單元測試**：它只是用 publishable 金鑰與 `Authorization: Bearer <ctx.accessToken>` 建立 supabase-js client（和 `auth.ts` 的 `createGetClaimsVerifier` 一樣，T-003 也沒有單元測試它）；第一個實際呼叫它的 endpoint 單，會在 CI `db` job 對真實 Supabase 驗證（TASKS §5.1 B-033）。`SupabaseEnv` 沒有 secret 金鑰欄位，所以這個入口不可能用 secret 金鑰（§4.9、CLAUDE.md 第 14 點）。
7. **「本機 DB 整合測試」的做法**（TASKS T-007 列；RUNBOOK §3 能力表：Claude Code 的 runner 不能跑 `supabase`／`docker`／`psql`，CI `db` job 目前只跑 `supabase test db` 與 health，要加 TypeScript 對資料庫的測試得改 `.github/scripts/db-job-verify.sh`，那是 SRE 的 O-xxx，不在本單）：改成兩段相扣——① `tooling/db-provider-call.test.ts` 靜態對照「TS 寫入的欄位清單」＝「T-006 migration 給 `authenticated` 的 INSERT 欄位權限」；② 那個權限本身由 T-006 的 pgTAP（`(AC-T6-2) authenticated may INSERT only these provider_call columns`、`(AC-T6-9)` 寫入與 CHECK）在本 PR 觸發的 CI `db` job 對真實資料庫斷言。任一邊改了欄位，另一邊就會失敗（突變 M3 在 box 上兩邊都失敗）。真正用 supabase-js 對本機 Supabase 寫入的測試，記在 TASKS §5.1 B-033。
8. **架構規則**：新增 dependency-cruiser 規則 `arch31-db-no-providers`（`from` `^supabase/functions/_shared/db/`、`to` `^supabase/functions/_shared/providers/`，含 adapter 與 `registry.ts`），名稱不用 `adr008-` 開頭，因為它執行的是 ARCHITECTURE §3.1 表格的「禁止：供應商」，不是 ADR-008 編號的條文。測試沿用 `tooling/arch-rules.test.ts` 的 fixture 做法（違規範例＋既有合法範例），真實程式碼由 `pnpm arch` 掃描、0 違規。
