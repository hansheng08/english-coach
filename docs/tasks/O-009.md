## 介面
```ts
type Mutant = { id: string; file: string; before: string; after: string; expectFail: string[] };
type MutantsFile = { task: string; mutants: Mutant[] };                  // docs/qa/mutants/<編號>.json
type MutantResult = { id: string; status: 'killed' | 'survived' | 'unexpected'; failedTests: string[] };
type MutantsReport = { task: string; total: number; killed: number; survived: string[]; results: MutantResult[] };
type Comment = { id: number | string; body: string | null; url?: string };
type SummaryInput = { task: string; sha: string; vitest: unknown; changed: string[]; execution?: unknown; mutants?: MutantsReport };
export function validateMutants(data: unknown, o: { task: string; root: string }): Finding[];     // run-mutants.mjs
export function runMutants(o: { file: string; root: string; runner: string[] }): MutantsReport;   // run-mutants.mjs
export function renderSummary(o: SummaryInput): string;                                           // verify-summary.mjs
export function lintReport(r: { id: string; path: string; text: string }): Finding[];             // report-lint.mjs
export function lintComments(comments: unknown): Finding[];                                       // comment-lint.mjs
export function branchId(branch: string): string | null;  // task-file.mjs："task/T-023"→"T-023"、"fix/Q-012"→"Q-012"、其他→null
```
CLI（工作目錄為 repo 根目錄）：
```text
node tooling/run-mutants.mjs --file <mutants.json> --out <report.json> [--root <dir>] [-- <runner argv...>]
node tooling/verify-summary.mjs --task <id> --sha <sha> --vitest <json> --changed <list.txt> [--execution <json>] [--mutants <report.json>]
node tooling/report-lint.mjs <report.md> [<report.md> ...]
node tooling/comment-lint.mjs --comments <comments.json>
```
輸出格式同 O-008：通過時 stdout `<tool>: OK <目標>`、exit 0；失敗時 stderr 每個 Finding 一行 `<tool>: FAIL <file>:<line>: <rule>: <message>`，最後一行 `<tool>: <N> error(s)`，exit 1。參數錯誤、檔案讀不到、JSON 解析失敗、未知選項、未捕捉例外一律 exit 1（rule `USAGE` 或 `INPUT`）。`verify-summary` 成功時 stdout 是 Markdown 摘要（不印 OK 行）。

### run-mutants 規則
- 執行器：`--` 之後的 argv；省略時為 `pnpm exec vitest run --reporter=json --outputFile={report}`。`{report}` 換成暫存檔路徑；以 `child_process.spawnSync` 不經 shell 執行，cwd＝`--root`（預設 `.`），單次逾時 600 秒。
- `MU-SCHEMA`：頂層不是物件、有多餘欄位、`task` 不等於檔名（去掉 `.json`）、`mutants` 不是非空陣列；任一筆缺欄位或有多餘欄位、`id` 不符 `M<數字>` 或重複、`before` 為空、`after` 等於 `before`、`expectFail` 不是非空字串陣列。
- `MU-TARGET`：`file` 是絕對路徑、含 `..`、不存在或不是一般檔案，或符合 `**/*.test.*`、`**/*.spec.*`、`tooling/fixtures/**`、`docs/**`、`.github/**`、`.claude/**`、`**/node_modules/**`。
- 有任何 `MU-SCHEMA`／`MU-TARGET` 時不執行任何測試。
- `MU-BASELINE`：未突變時執行器 exit 非 0，或報告缺漏、無法解析、有 `failed` 的測試；此時不套用任何突變。
- `MU-ANCHOR`：`before` 在目標檔出現 0 次或超過 1 次（以當下原始內容計）。
- 判定：執行器 exit 非 0 且報告中至少一個 `failed` 測試的 `fullName` 含 `expectFail` 任一字串 → `killed`；exit 0 → `survived`（`MU-SURVIVED`）；exit 非 0 但失敗的測試都不含 `expectFail` → `unexpected`（`MU-UNEXPECTED`）；exit 非 0 且報告缺漏或無法解析、或逾時 → `MU-RUNNER`。
- 還原：每筆執行完（含例外、逾時）立即寫回原始位元組；全部結束後再比對每個目標檔的 SHA-256 與開始時相同，不同 → `MU-RESTORE`。
- `--out` 一律寫出 `MutantsReport`（有錯誤時也寫出已完成的部分）；全部 `killed` 才 exit 0。stdout 每筆 `killed` 一行 `run-mutants: KILLED <id>`。

### report-lint 規則（檢查 `docs/reports/<編號>.md`）
- `RL-TITLE`：第 1 行不是 `# <編號> 報告`，或編號與檔名不同。
- `RL-SECTION`：缺 `## 完成摘要`、`## 未完成事項`、`## 需要人類決定的問題`、`## 權限被拒` 任一個。
- `RL-LINES`：全文超過 80 行。
- `RL-PASTE`：任一行（含程式碼區塊內）符合貼上的測試輸出：行首（可有空白）為 `Test Files`、`Tests`、`Start at`、`Duration` 後接 2 個以上空白；行首為 `✓`、`✗`、`×`、`❯` 後接空白；含 `passed (<數字>)`；行首 `Files=<數字>, Tests=<數字>`；行首 `Result: PASS` 或 `Result: FAIL`。
- `RL-NUMBER`：`## 權限被拒` 以外的行，出現前面不是 `-`、英數字或 `.` 的數字，後接（可有空白與「個」「項」「支」）`test`、`tests`、`passed`、`failed`、`skipped`、`測試`、`突變`、`mutant`、`mutants`（英文不分大小寫）。例：`共 12 個測試` 失敗；`AC-O9-1 測試` 不失敗。

### comment-lint 規則（輸入：留言 JSON 陣列）
- 開頭文字＝`body`（`null` 視為空字串）去掉開頭重複出現的空白與 `#`、`*`、`_`、`>`、`` ` ``、`~`、`【`、`[`、`「` 後的內容。
- `CM-TECHLEAD`：開頭文字以 `TechLead Review` 開頭（不分大小寫，`TechLead` 與 `Review` 之間可有 0 個以上空白）。
- `CM-QA-RERUN`：開頭文字以 `QA` 開頭且下一個字元不是英文字母，而且 `body` 有任一行同時含「本機標記」（`本機`、`重跑`、`box`、`worktree`、`locally`、`rerun`、`re-run`，英文不分大小寫）與「指令」（`pnpm check`、`pnpm db:test`、`pg_prove`、`supabase test db`）。
- Finding 的 file 為 `comment/<id>`、line 為 1；空陣列 → `comment-lint: OK 0 comment(s)`。輸入不是陣列、元素缺 `id`、`body` 不是字串或 `null` → `INPUT`。
- 已知限制（不是缺陷，測試要固定這些行為）：所有留言作者都是 `hansheng08`，只看開頭文字分角色；開頭不是 `TechLead Review` 的留言即使中間提到也不算；QA 寫「不在本機重跑 pnpm check」也會被判違規（寧可誤報）。

### verify-summary 規則
- 第 1 行 `## 自動驗證摘要（<task> @ <sha 前 7 碼>）`，之後依序 `### 測試`、`### 突變`、`### 權限被拒`、`### 變更檔案` 四節；數字一律由輸入計算。
- 測試：由 Vitest JSON 的 `testResults[].assertionResults[].status` 計算測試檔數與 passed／failed／skipped（`pending`、`todo`、`skipped` 合計）數；有 failed 時加一行 `結果：失敗`，否則 `結果：通過`。
- 突變：有 `--mutants` 時列 `killed／total` 與每個非 `killed` 的 id 與狀態；沒有時寫 `未執行（沒有 docs/qa/mutants/<task>.json）`。
- 權限被拒：有 `--execution` 時取所有 `type` 為 `result` 的事件的 `permission_denials`，列次數與每筆 `tool_name`、`tool_input.command`；沒有時寫 `不適用（未提供 execution 紀錄）`。
- 變更檔案：列數量與清單（空行忽略）。
- `INPUT`：Vitest JSON 缺 `testResults` 或結構錯；`--execution` 不是陣列或沒有 `result` 事件；`--mutants` 不符 `MutantsReport`；`--sha` 不是 7～40 位十六進位。

## 驗收標準
- **AC-O9-1** mutants.json 驗證：`MU-SCHEMA`、`MU-TARGET` 各條件都 exit 1，且不呼叫執行器；合格檔 exit 0。
- **AC-O9-2** run-mutants 判定：`MU-BASELINE`、`MU-ANCHOR`、`killed`、`MU-SURVIVED`、`MU-UNEXPECTED`、`MU-RUNNER` 依上方規則；全部 killed 才 exit 0；`--out` 的報告欄位與判定一致。
- **AC-O9-3** run-mutants 還原：每筆突變後、執行器失敗或逾時後，目標檔都回到原始位元組；比對不符時 `MU-RESTORE` exit 1。測試一律在暫存目錄的 fixture 副本執行，不改 repo 內的檔案。
- **AC-O9-4** verify-summary：四節內容與輸入一致（含失敗、略過、無突變、無 execution 的寫法）；`INPUT` 各條件 exit 1 且 stdout 為空。
- **AC-O9-5** report-lint：`RL-TITLE`、`RL-SECTION`、`RL-LINES`、`RL-PASTE`、`RL-NUMBER` 各自在壞輸入上 exit 1；80／81 行邊界；多個錯誤全部列出；本 repo 現有的 `docs/reports/O-008.md` 經 lint 的結果在報告「設計決定」寫明（通過或列出 rule id）。
- **AC-O9-6** comment-lint：`CM-TECHLEAD`、`CM-QA-RERUN` 依規則判定；只引用 CI run 的 QA 留言、run-task 摘要留言、自動驗證摘要不誤判；已知限制的三種行為有測試固定。
- **AC-O9-7** fix 分支：`branchId` 只接受 `task/` 加 `[TQOAP]-<3 位數>`與 `fix/` 加 `Q-<3 位數>`，其他回 null；`scope-check --branch fix/Q-012` 以 `## 分支` 為 `fix/Q-012` 的任務單集合判定，並隱含允許 `docs/qa/mutants/Q-012.json`；找不到任務單 → `SC-NOTASK`；`ac-coverage` 對 fix 分支同樣運作。O-008 既有測試全部仍通過。
- **AC-O9-8** fail-closed 與依賴：四支 CLI 缺參數、未知選項、檔案不存在、壞 JSON 都 exit 1（`USAGE`／`INPUT`）且不印 OK；以子行程實際斷言 exit code；只 import `node:` 與 `./`；不含 `|| true`、`continue-on-error`、吞掉錯誤後 exit 0 的 `catch`；不改 `package.json`／`pnpm-lock.yaml`。

## 限制
- 只用 Node 內建模組；不新增套件、不連網。腳本是 ESM（`.mjs`），在 Node 24 直接執行。
- 測試寫成 `tooling/*.test.mjs`；CLI exit code 以 `child_process.spawnSync(process.execPath, …)` 實際斷言。run-mutants 的測試用 fixtures 內的假執行器（以 `process.execPath` 執行），不得在測試裡再呼叫 vitest 或 pnpm；所有突變都在 `os.tmpdir()` 下的副本進行。
- `run-mutants` 不呼叫 git、不寫 `--out` 與目標檔以外的檔案；`comment-lint` 與 `verify-summary` 只讀檔，不呼叫 `gh` 或網路（讀 GitHub 留言由 SRE 接線負責）。
- 讀檔、搜尋一律用內建 Read／Grep／Glob 工具；不要用 Bash 的 `cat`、`grep`、`head`、`ls`、`sed`（設定已擋，被擋後換寫法重送會讓 run 失敗）。
- commit 與 push 從第一次就分成三次各自獨立的 Bash 呼叫，依序為 `git add <明確檔案路徑…>`、`git commit -m "[Claude] O-009 …"`、`git push -u origin task/O-009`；每一次都不得含 `&&`、`;`、`|`、`2>&1` 或其他指令（O-008 的 run 因複合 push 被擋後再分開送，被判定為拆開重送）。
- pgTAP 結果、`.github/` 接線、run-task SKILL 改版不在本單 AC 範圍。

## 驗證方式
`pnpm check` 跑到通過；任務單不另列指令。

## 結束時
1. 在指定的分支上 commit 並 push，不得動 main。
2. 把結果寫到 docs/reports/O-009.md：完成摘要、變更檔案、測試結果、未完成事項、需要人類決定的問題。
3. 測試結果、突變結果、權限被拒以 workflow 自動產生的摘要與 PR 觸發的 CI run 為準，報告不重貼。

## SRE 接線（Claude Code 不做；不是 AC；Claude 的 run 成功後由 SRE 在同一分支加 commit）
- `ci.yml`：`taskcheck` 擴及 `fix/**`（push 與 PR）；新增 `mutants` 步驟：`docs/qa/mutants/<branchId>.json` 存在才跑 run-mutants，不存在時明確印出並列為略過；`verify-summary` 寫入 job summary；`report-lint` 檢查本分支變更的 `docs/reports/*.md`；`ci-ok` 同步更新。
- `claude-run-task.yml`：Claude 之後跑 `report-lint docs/reports/$TASK.md`（失敗 → `outcome=report_lint_failed`）與 `verify-summary`，併入既有 run-task 摘要留言；`run-task-outcome.sh` 與測試同步。
- 新增 `g3-comment-guard.yml`：`pull_request`、`issue_comment`、`pull_request_review`、`pull_request_review_comment` 觸發；只處理標題 `[G3]` 開頭的 PR；以 `GITHUB_TOKEN`（`contents: read`、`pull-requests: read`、`issues: read`、`statuses: write`）讀三種留言並跑 comment-lint，結果寫成 PR head 的 commit status `g3-comment-guard`；讀取失敗也判失敗。
