## 背景（開始前先讀）
- **發現 (a) 會跟著轉址**（TechLead 讀 main `09a3ef5` 核對）：
  - `supabase/functions/_shared/providers/azure-speech/transport.ts:64-69`、`gemini/transport.ts:76-81` 呼叫 `fetch` 時沒有設 `redirect`，用的是預設的 `follow`。
  - 金鑰放在自訂標頭（`pronunciation.ts:91`、`tts.ts:21` 的 `Ocp-Apim-Subscription-Key`；`gemini/transport.ts:78` 的 `x-goog-api-key`）。依 Fetch 標準，跟著轉址時只有 `Authorization` 這類標頭在跨來源時會被拿掉，**自訂標頭會原樣送到 `Location` 指的網址**。
  - 另外，§5.4 與 §5.6.4 的錯誤表都寫「3xx → `unavailable`」，但預設 `follow` 時 adapter 根本看不到 3xx：現有的 3xx 測試只測 `classify…Error` 純函式，沒有測 `fetch` 的設定。
  - 前例：`_shared/news/http.ts:72` 已經用 `redirect: 'manual'`，`:90` 處理 `opaqueredirect`／`status === 0`。
- **發現 (b) 金鑰沒有 trim**：
  - `config/provider-keys.ts:12` 用 `value.trim().length === 0` 判斷空白，但 `:20` 回傳原值；`:38` 同樣判斷、`:46` 回傳原值的 `key`；`config/paid.ts:9`、`:17`（`GEMINI_PAID_API_KEY`）同樣。
  - 遮蔽用 `text.split(key)`（`gemini/errors.ts:10`、`azure-speech/errors.ts:11`）。金鑰帶前後空白或換行（例如貼進 Supabase secrets 時多了換行）時，`Headers` 會把標頭值前後的空白去掉再送出；伺服器若在錯誤內容裡帶出金鑰，帶出的是 trim 後的字串，`split(原值)` 找不到，金鑰就會留在 `ProviderError.message`。
- **嚴重度**：低（兩家的網址都是固定的 https 主機，目前沒有已知的轉址；金鑰多空白要設定出錯才會發生），但後果是金鑰外洩（NFR-05），修法小，所以修。
- 既有程式：`config/provider-keys.ts`、`providers/azure-speech/`、`providers/gemini/`（含各自 `test/fake-fetch.ts`）、`_shared/news/http.ts`（只讀，參考寫法）。
- `CLAUDE.md` §4～§7；`docs/RUNBOOK.md` §3.1：你只能跑 `pnpm install --frozen-lockfile` 與 `pnpm check` 系列；沒有網路、沒有金鑰。

## 目標
Azure Speech、Gemini 兩個 adapter 的每次 `fetch` 都不跟著轉址，3xx 與 `opaqueredirect` 回 `unavailable`；`loadGeminiKey`、`loadGeminiPaidKey`、`loadAzureSpeechConfig` 回傳 trim 後的金鑰。其他行為不變，既有測試（含 QA 的）照樣通過。

## 介面
不改任何匯出的名稱與型別。`fetch` 的第二個參數多一個 `redirect: 'manual'`；`loadGeminiKey`、`loadGeminiPaidKey` 回 `ok(trim 後的值)`；`loadAzureSpeechConfig` 回 `ok({ key: trim 後的值, region })`（`region` 的處理不變）。

## 驗收標準
- **AC-T17-12**（§5.4、§5.6.4 的 3xx 列）`azure-speech/transport.ts`、`gemini/transport.ts` 呼叫 `fetch` 時都帶 `redirect: 'manual'`；發音評估、TTS、Gemini `generate`、`stream` 四條路徑都一樣。
- **AC-T17-13** 回應是 3xx（含 301、302、307、308）時不再送出第二個請求，回 `unavailable`，訊息含 HTTP 狀態；回應的 `status` 是 0 或 `type` 是 `opaqueredirect` 時也回 `unavailable`（訊息寫 `redirect not followed`）；這兩種情況 `fetch` 都只被呼叫 1 次。
- **AC-T17-14**（§5.4.2、§5.5）`loadGeminiKey`、`loadGeminiPaidKey`、`loadAzureSpeechConfig` 回傳的金鑰是 trim 後的值；判斷「沒有／空白」的條件與錯誤訊息不變。
- **AC-T17-15**（§5.5 第 3 點）金鑰設定成前後帶空白或換行時，伺服器錯誤內容帶出 trim 後的金鑰 → `ProviderError.message` 不含金鑰、含 `[redacted]`（從 `load…` 讀到的值一路傳進 adapter）。
- **AC-T17-16** 其他行為不變：既有的 Claude 測試與 QA 測試（`azure-speech.qa.test.ts`、`gemini.qa.test.ts`）不改也照樣通過；QA 突變檔 `docs/qa/mutants/T-014.json`、`T-015.json`、`T-017.json` 每筆的 `before` 字串在該檔仍剛好出現 1 次（不改寫那幾行的文字，只在旁邊加程式）。

## 測試的寫法
- 只用各 adapter 自己 `test/` 裡的假 `fetch`；假 `fetch` 要能記錄 `init.redirect`（`FetchCall` 加一個欄位，既有欄位不動）。不連網、不讀環境變數。
- `status` 是 0 的回應：`new Response()` 不能建 status 0，用 `Response.error()`，或在假 `fetch` 裡回一個 `status: 0`、`type: 'opaqueredirect'`、`ok: false` 的物件（型別用 `Response` 的子集，不用 `as unknown as`）。
- TC-26 的「`before` 剛好 1 次」由 CI 的 run-mutants 驗證；本機用 `pnpm check` 即可，不另寫測試。
- 測試裡的金鑰一律是假字串，不得像真的金鑰。
