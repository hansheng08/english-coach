- 事實（原始日誌，2026-11-28 台北時間；`Start local Supabase`／`supabase start` 步驟）：
  - 失敗 4 次，錯誤完全相同：`failed to bind host port 0.0.0.0:54322/tcp: address already in use`（`supabase_db_english-coach`，只出現在第一個要綁埠的資料庫容器）。run 與 job：45945740535（`db`，O-025／#86）、46090463476 第 1 次嘗試（`db`，#110）、46095403592（`e2e`，#116）、46098320260（`e2e`，#118）。
  - 失敗的 4 次日誌都有 `error from registry: Rate exceeded`，但成功的 job 也有（同日抽查的 6 個成功 `db`／`e2e` job 中 4 個有 1～2 次，其中一個還有 8 張映像連續 `Data limit exceeded`）。CLI 3.2.0 對每個映像自動重試（4 秒、8 秒），並依序改試 GHCR、Docker Hub；每次重試後都拉取成功。映像速率限制只拖慢啟動（約 51～65 秒），不是失敗直接原因。
  - 每個 job 在獨立 VM 上：`docker info` 顯示 `Containers: 0`、`Running: 0`；同一個 run 的 `db` 與 `e2e` 有不同的 runner 編號，且多個成功的 run 中兩個 job 的 Postgres 同時在跑（時間重疊）卻都綁到 54322。所以不是兩個 job 搶同一台機器的埠。
  - CLI 3.2.0 只執行一次 `docker start`、沒有啟動重試，因此不是「第一次部分啟動留下容器」的副作用；失敗後 CLI 自己做回滾（`Stopping containers...`）。
  - 日誌證明 54322 在那台 VM 上、`docker start` 當下已被占用，但看不到是誰占用。假設（設計不依賴此假設）：ephemeral 埠範圍（預設 32768～60999）包含 54320～54329，大量映像下載連線的來源埠偶然落在 54322。4 次失敗落在兩個區域各 2 次（eastus2、westus2），樣本太小不能當作區域結論。此假設由接線後的失敗診斷驗證，見「接線 PR run 驗證項」。
- 影響（原始 job 時間）：失敗的 `e2e` 約 78～86 秒、`db` 約 46～56 秒；加上 `ci-ok` 失敗，之後要人按 Re-run（#110 隔了約 39 分鐘才重跑）。11-27 05:25 起約 30 小時內 44 次完成的 PR 觸發 run 中有 4 次受影響（含 O-025 那次），約每 11 次一次。
- 決定：不靠猜根因；做兩件與根因無關、且失敗時一定留下證據的事：（1）有限次、帶退避、僅針對暫時性錯誤的自動重試；（2）失敗時印出診斷，下一次發生就能證實或推翻上述假設。外加一個低成本預防：預留 54320～54329 不被當作 ephemeral 來源埠。
- 不選的方案（理由）：映像快取（`docker save` 打包還原，載入大型 tarball 的時間預期接近重新拉取（未實測）；快取只能由 main 產生，main 的 push 不啟動 Supabase；占用 10 GB 配額；失敗原因也不是拉取）；改 `SUPABASE_INTERNAL_IMAGE_REGISTRY`（設了之後只剩單一候選，反而失去 GHCR 與 Docker Hub 的自動備援）；升級 CLI（3.3.0、3.4.0 的 release notes 看不出與本問題有關，3.4.0 還改了預設啟動方式，風險另案評估，CLI 維持釘 3.2.0）。

## 目標
`e2e`、`taskcheck`、`db` 三處啟動本機 Supabase 時：暫時性失敗在同一個 job 內自動恢復（最多 3 次嘗試），無法恢復或不是暫時性錯誤時仍然失敗（fail-closed），並留下可判讀的證據。

## 定義（本節凍結）
- 失敗分類（輸入是 `supabase start` 的完整輸出，不分大小寫）：
  - `port-bind`：含 `failed to bind host port`、`address already in use` 或 `port is already allocated` 其中之一。
  - `registry`：不屬 `port-bind`，且含 `error from registry`、`Rate exceeded`、`Data limit exceeded`、`toomanyrequests`、`TLS handshake timeout`、`unexpected EOF` 或 `i/o timeout` 其中之一。
  - `fatal`：其他一切，包含空字串、設定錯誤、資料庫健康檢查逾時、遷移失敗。判斷不了就是 `fatal`。
- 重試規則：最多 3 次嘗試（含第一次）。只有 `port-bind`、`registry` 才重試；第 1 次失敗後等 10 秒、第 2 次失敗後等 20 秒；第 3 次失敗、`fatal`、或「清理後仍有非 Docker 行程在監聽 54320～54329」一律不再重試。
- 兩次嘗試之間（SRE 腳本）：印診斷（只印埠號、狀態、行程名稱、容器名稱與狀態、ephemeral 範圍；不印環境變數）、`supabase stop --no-backup`、依規則等待。
- 預留埠（SRE 腳本，第一次嘗試前）：把 54320～54329 加進 `net.ipv4.ip_local_reserved_ports`（保留 runner 原有值）。這是預防，不是驗證；設定失敗只發 `::warning` 並繼續，讀回值要印出來。
- 證據行（固定開頭 `supabase-start:`）：每次嘗試一行（第幾次、分類、等待秒數），結束時一行總結（成功在第幾次或失敗原因）。
- 最終結果：只要有任何一次 `supabase start` 結束碼為 0 就成功；其餘一律非 0。

## 介面
```ts
export type FailureKind = 'port-bind' | 'registry' | 'fatal';
export const MAX_ATTEMPTS: number;
export const RETRY_DELAYS_SEC: readonly number[];
export function classifyStartFailure(output: string): FailureKind;
export type Decision = { retry: true; delaySec: number } | { retry: false; reason: string };
export function decideRetry(input: { attempt: number; kind: FailureKind; portHeldByOther: boolean }): Decision;
```
命令列（`tooling/supabase-start-policy.mjs`）：
```text
classify <檔案>                    stdout：port-bind／registry／fatal
decide <第幾次> <分類> <held 0|1>   stdout：retry <秒> 或 stop <原因>
結束碼：0 成功、2 輸入錯誤（缺參數、非整數、超出 1～MAX_ATTEMPTS、未知分類、held 不是 0／1、檔案讀不到）
```

## 驗收標準
- AC-O31-1：`classifyStartFailure` 依「定義」分類；`port-bind` 優先於 `registry`；空字串與未知文字是 `fatal`；日誌混有其他行也能命中。
- AC-O31-2：`decideRetry` 依「定義」：`port-bind`／`registry` 在第 1、2 次回 `retry` 且秒數取自 `RETRY_DELAYS_SEC`；第 3 次、`fatal`、`portHeldByOther` 為 true 回 `stop` 並附原因；`attempt` 不是 1～`MAX_ATTEMPTS` 的整數時丟錯（fail-closed）。
- AC-O31-3：命令列的輸出格式與結束碼如「介面」；任何輸入錯誤都是結束碼 2，且不印出 `retry`。
- AC-O31-4（SRE）：`.github/scripts/supabase-start.sh` 轉傳所有參數給 `supabase start`；第 1 次成功不呼叫 `stop`、不等待；`port-bind` 或 `registry` 後以 `supabase stop --no-backup` 清理並重試；3 次都失敗、`fatal`、清理後仍有非 Docker 行程監聽時非 0 結束；每次失敗都印診斷；輸出經與 `db-job-verify.sh` 相同的金鑰遮蔽；印出「證據行」。
- AC-O31-5（SRE）：`ci.yml` 的 `e2e`、`taskcheck` 與 `db-job-verify.sh` 啟動 Supabase 一律經過該腳本，旗標（`-x` 清單、`--workdir`）與現況相同；`ci.yml` 與 `.github/scripts/` 不得再有直接的 `supabase start`（腳本本身除外）。
- AC-O31-6（SRE）：預留埠在第一次嘗試前執行；權限不足時 `::warning` 且不中止；已有的預留值被保留。
- AC-O31-7（SRE）：不新增 job；`.github/ci-budget.json` 的 `ci.yml` 上限不變（7）；三個 job 的 `timeout-minutes` 不變。`db` job 必須能執行策略模組（Node）：若該 job 還沒有 Node，在同一個 `db` job 加 `setup-node` 步驟（沿用 `ci.yml` 其他 job 已釘的 action，不新增 job、不調高逾時）；不得另寫一份 shell 分類路徑。
- AC-O31-8（SRE）：`docs/RUNBOOK.md` 新增小節，寫明根因判斷（假設與診斷如何驗證）、重試規則、診斷怎麼讀、如何從日誌統計「靠重試救回」的次數、CLI 仍釘 3.2.0 及不選方案的理由。
- AC-O31-9：突變必須被抓到：分類順序顛倒；`fatal` 也重試；重試次數或秒數改變；`portHeldByOther` 不再生效；腳本改成永遠回 0；腳本不清理就重試；`ci.yml` 或 `db-job-verify.sh` 改回直接 `supabase start`。削弱後仍通過任何測試，本 AC 失敗。
- AC-O31-10：本單新增或修改的檔案沒有未允許的 `|| true`、`continue-on-error`；清理指令失敗要記錄，不得吞掉原始啟動失敗。
