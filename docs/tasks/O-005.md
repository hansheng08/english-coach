## 背景（開始前先讀）
- Q-26：`db-job-verify.sh` 用 `POST /auth/v1/signup` 取 token，需要 `enable_signup = true`，與 Q-01／ARCHITECTURE §7「關閉註冊」衝突。Hansheng 核准方案 B：改用本機 Auth Admin API（secret key）建已確認帳號再登入。
- Q-27：`pnpm install --no-frozen-lockfile` 在 `.claude/settings.json` 與 `claude-run-task.yml` 不一致；`Read(**/.env.*)` 連 `.env.example` 一起擋（Claude Code 的 deny 一律優先於 allow）。
- B-003：run-task SKILL 補憲章 v5 §13 第 11、12 條與「權限被拒」欄位；`run-task-outcome.sh` 對非 `success` 明確正規化（複審備註 3：`claude` 為 `skipped`／`cancelled` 時原樣回傳）。
- `adr010-keycheck.sh` 寫死 `o003-env`，T-003 的產品函式需要乾淨前綴。repo 文件沒有指定名稱，本單定為 `adr010-env`。
- 執行環境能力表（RUNBOOK §3）：box 無 Docker／Supabase CLI，`db` job 的實際行為只能在 PR 觸發的 CI 驗證。

## 目標（一句話）
讓產品設定可以照 Q-01 設 `enable_signup = false` 而 `db` job 仍能驗 401／401／200，並把 lockfile 更新、`.env.example` 讀取、金鑰檢查前綴與 run-task 結果正規化一次整理好，T-003 寫單時不再卡住。

## 實作限制
- 驗證腳本預設失敗（憲章 v5 §5）；不得新增未附理由的 `|| true`、`|| :`、`|| exit 0`、`continue-on-error`。
- 不印任何金鑰、密碼、token 的值；測試裡的假 token 在執行時產生，不寫進檔案。
- `db-job-verify.sh` 只能在 CI 執行（box 無 Docker）。
