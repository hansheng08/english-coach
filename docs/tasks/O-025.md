## 目標
讓 ac-coverage 用與 Vitest／TAP 相同的規則，把「實際跑過且最終通過」的 Playwright 測試算進覆蓋；缺漏或無效的 Playwright 報告必須 fail-closed。並由 SRE 把 e2e 的 JSON 結果送到 `taskcheck` job（不新增 job）。

## 介面

### Playwright JSON 怎麼算通過（本單凍結）
讀 Playwright JSON reporter（`@playwright/test` 的 json reporter；T-018 用 `^1.55`）。遞迴走根物件的 `suites[]`（套件可再嵌 `suites`），每個 `specs[]` 的每個 `tests[]` 算一筆。覆蓋比對用的名稱＝由外而內的 suite `title` 加上 spec `title`（中間一個空白）；專案名稱可不列入名稱，同一則測試在多個 project 出現時，任一筆算通過即可，任一筆最終失敗則 `CV-FAILED`（與 Vitest 相同）。

Playwright JSON 的欄位（不要跟 Vitest 的 `status` 搞混）：

- 測試列的 `status`（即 `test.outcome()`）：`expected`、`unexpected`、`flaky`、`skipped`
- 測試列的 `expectedStatus`：`passed`、`failed`、`skipped`
- `results[]` 每一筆的 `status`：`passed`、`failed`、`timedOut`、`skipped`、`interrupted`；另有 `retry`（從 0 起算）

**算通過（等同 Vitest／TAP 的 `passed`）**，必須同時成立：

1. 測試列 `expectedStatus === 'passed'`（排除 `test.fail()` 這類 expected-fail）
2. 測試列 `status`（outcome）是 `expected` 或 `flaky`
3. `results` 非空，且**最後一筆** `status === 'passed'`

**不算通過**：`skipped`（outcome 或 `expectedStatus`，或沒有 `results`／未跑）；`unexpected`；expected-fail（`expectedStatus === 'failed'`，即使 outcome 是 `expected`）；最後一筆不是 `passed`（含 `failed`、`timedOut`、`interrupted`、先過後失敗）。相關測試最後失敗 → `CV-FAILED`；沒有任何通過的相關測試 → `CV-MISSING`。

**重試後才通過要算覆蓋**：outcome 為 `flaky`、`expectedStatus` 為 `passed`、最後一筆 result 為 `passed` 時，**算通過**。理由：Vitest／TAP 也只看最終 `status`；Playwright 的 `flaky` 表示經過重試後停在預期的通過狀態，AC 確實被觀察到通過。先失敗且最後仍失敗的不算，也不因為中間曾有一筆 `passed` 就放行。

缺檔、空檔、JSON 無法解析、根物件沒有 `suites` 陣列、或測試列缺少本單要讀的 `status`／`expectedStatus`／`results` 欄位：一律 `INPUT`（或 CLI 非 0），不得當成「沒有 Playwright 結果、只靠 Vitest 過關」。

### CLI（Claude 改 `tooling/ac-coverage.mjs`）
- 新增可重複的 `--playwright <file>`（寫法與既有 `--tap` 相同）。
- 至少要有 `--results`、`--tap`、`--playwright` 三者之一；可以只有 Playwright、沒有 Vitest JSON。
- 有傳 `--playwright` 時，每個路徑都必須存在、非空、且通過上一節的解析；任一失敗就整次失敗。
- 沒有傳 `--playwright` 時，行為與現況相同（只讀 Vitest／TAP）。這就是「e2e job 被略過」時工具層的契約：由接線決定要不要傳這個參數，工具本身不去猜 job 有沒有跑。

### e2e 被略過時（接線契約；寫進 `taskcheck.sh`／`ci.yml`）
以現行 `ci.yml` 為準，不要寫成 `has_web`：

- `e2e` 被略過（`has_e2e=false`，或不是 `pull_request`，或不是 full mode）時：`taskcheck` **不要**傳 `--playwright`，也不要因為沒有 Playwright 檔而 `INPUT`。若該任務單有只存在 Playwright 的 AC／TC，push 上的 `taskcheck` 仍可能 `CV-MISSING`；這與「以 PR 觸發的 `ci-ok` 為準」（O-015）一致。T-018 的 G3 是 PR，那時 `has_e2e=true` 且 `is_pr=true`，`e2e` 必須跑。
- `e2e` 有跑（success 或 failure、不是 skipped）時：必須產出並交給 ac-coverage 一份有效的 JSON；缺檔或無效就 fail-closed，不得默默略過。

不要新增 CI job，不要改 `ci-budget.json`。不要為了本單去改 `playwright.config.ts`（屬 T-018）；e2e 步驟用 CLI／環境變數加上 json reporter（例如在既有 `pnpm e2e` 加上 `--reporter=list --reporter=json`，並釘死輸出路徑）。

## 驗收標準
- AC-O25-1：符合「算通過」三條件的 Playwright 測試，與 Vitest／TAP 一樣算覆蓋；比對名稱為套件＋spec 標題，標題裡的 `(AC-…)`／`(TC-…)` 標籤必須被找到。
- AC-O25-2：略過、未跑、`unexpected`、expected-fail、以及最後一筆不是 `passed` 的測試都不算覆蓋；相關測試最終失敗要 `CV-FAILED`，否則沒有通過測試時是 `CV-MISSING`。
- AC-O25-3：先失敗再靠 retry 通過（outcome `flaky`、`expectedStatus` `passed`、最後一筆 `passed`）算覆蓋；先過後失敗或最後失敗不算。
- AC-O25-4：有傳 `--playwright` 但檔案缺漏、空、不是合法 JSON、或缺本單要的欄位時，必須是 `INPUT`／非 0，不得當成功。沒有傳 `--playwright` 時維持只讀 Vitest／TAP 的現況。
- AC-O25-5：突變必須被抓到：把 skipped／expected-fail 當成通過、缺檔或無效 JSON 當成沒有發現、不遞迴巢狀 `suites`、拿第一筆 result 而不是最後一筆（讓先過後失敗變成通過）。上述削弱若仍能通過測試，本 AC 失敗。
- AC-O25-6：本單新增或修改的檔案沒有未允許的 `|| true`、`continue-on-error`。
