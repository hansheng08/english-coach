## 目標
使用者上傳英文履歷（PDF 或 DOCX），在瀏覽器讀出文字並移除電話、Email、地址後，60 秒內產生 15～20 題、三類各至少 3 題、每題標出引用的經歷；新的取代舊的。按「刪除履歷」後原檔與解析文字從雲端刪除，舊題退休。

## 介面
§5.8.6 的 prompt 要點與輸出 schema、§4.9 第 4 點的三步照 ARCHITECTURE；以下是 TechLead 補的決定：
```ts
// supabase/functions/_shared/ai/resume-questions.ts（新增）
export const RESUME_TEXT_MAX_CHARS = 6000;  export const RESUME_QUESTIONS_TIMEOUT_MS = 45_000;   // maxOutputTokens 4096
export function generateResumeQuestions(llm: LlmProvider, redactedText: string): Promise<Result<readonly ResumeQuestion[], ProviderError>>;
// supabase/functions/api/resume.ts（新增）；RouteKey 加 'POST /resume'、'DELETE /resume'
export const postResume: Route;  export const deleteResume: Route;
// 新 migration 的 SQL 函式（security invoker，以使用者身分執行）
//   replace_resume(p_storage_path text, p_file_name text, p_pii_removed jsonb, p_redacted_text text, p_questions jsonb) returns uuid[]
// packages/contracts/src/resume.ts：PiiCountsSchema、ResumeUploadSchema（照 §4.21 的形狀）、sanitizeResumeFilename(raw): string | null
```
- **`replace_resume`**：一個交易裡依 §4.9 第 4 點的前兩步退休舊履歷題、刪舊 `resume` 列，再寫新 `resume` 列（含 `file_name`、`pii_removed`，§4.21：換新履歷時檔名與計數一併換成這一次的）與新題目（`source = 'resume'`、`resume_id = user_id`、`cited_experience`）；任何一步失敗整筆回復。舊的 Storage 原檔在函式成功之後才刪（第 3 步），刪失敗只寫 log、回應照常成功（新履歷已生效），報告記下。
- **`postResume` 順序**：body `{storagePath, redactedText, originalFilename, piiRemoved}`（`ResumeUploadSchema`，§4.21；`storagePath` 要是 `<user_id>/resume/` 開頭、`.pdf` 或 `.docx` 結尾；`redactedText` trim 後非空；`originalFilename` 先跑 `sanitizeResumeFilename`（只取最後一個 `/` 或 `\` 之後、去控制字元與 NUL、≤ 200 字元、副檔名只允許 `.pdf`／`.docx`）再驗證，空或不合 → 400 `validation`、`path` 是 `originalFilename`；`piiRemoved` 是 `{phone, email, address}` 三個非負整數，缺欄或不合 → `path` 是 `piiRemoved` 或 `piiRemoved.<欄位>`）→ `resolve('llm', …, sumPaidUsageThisMonthNtd)` → `generateResumeQuestions`（只送前 6,000 字）→ 失敗照 §5.0.4 回錯誤、**舊履歷與舊題不動** → `replace_resume`（帶清理後的檔名與計數）→ 刪舊原檔 → 200＋題目清單。**檔名不送 LLM**（`generateResumeQuestions` 的輸入只有去個資後的文字，§5.8.6）、不寫 log；計數由前端用同一次 `redactPii` 的 `removed` 填入，伺服器不再算一次（去個資在瀏覽器做，§7）。
- **`deleteResume`**：照 §4.9 第 4 點三步；第 1 步成功、第 2 步失敗回 500 `db_failed`（安全的中間狀態，重試即可）；第 3 步失敗回 502 `storage_failed`（`op: 'delete'`，可重試）。沒有履歷 → 404 `not_found`（`entity: 'resume'`）。成功回 `{deleted: true}`。
- **migration**：`resume` 表加 `file_name text not null`、`pii_removed jsonb not null`（§4.21；目前沒有任何程式寫 `resume`，不需要回填舊列，套用時若已有列就停下寫進報告）；`resume` bucket（`public = false`、10 MB）、`storage.objects` 的 `resume_select_own`、`resume_insert_own`、`resume_delete_own`（條件照 §4.12.1）；`replace_resume` 函式與 `grant execute … to authenticated`。
- **前端**：路由 `/resume`（`RequireSession`）；5 個狀態照 `resume.md` §1；上傳流程：`extractResumeText` → `redactPii`（取 `removed` 當 `piiRemoved`）→ 上傳到 `<user_id>/resume/<uuid>.<副檔名>` → `POST /resume`（帶 `File.name` 當 `originalFilename`、`piiRemoved`）；`POST /resume` 失敗時前端刪掉剛上傳的那個檔（盡力而為，失敗只記 log），舊履歷照常。`ApiClient` 加 `getResume()`（讀 `resume` 與未退休的履歷題，回 `fileName`、`piiRemoved`、`uploadedAt`；本版不新增 `GET /resume` 端點，§5.1 的端點表沒有它，§4.21 說的「讀取」由這個方法在 `api/supabase/` 以使用者身分讀表，RLS 限本人）、`uploadResumeFile`、`createResume`、`deleteResume`；Storage 上傳或刪除失敗一律轉成 `storage_failed`（502、可重試）的 `AppError`。照 §9.1.7：supabase 版方法只用組成根注入的 `deps.fetch`、`deps.getAccessToken`，畫面經 `useApi()`，`features/**` 不直接 `fetch`、不直接用 supabase-js；新方法在 `api/test/fakes.ts` 補預設值並設必填（沒有這個檔案時由本單建，方法暫時選填，TASKS 備註）。設定頁履歷列（T-020 建）補上檔名與題數。

## 驗收標準
- **AC-T36-1**（§5.8.6）`generateResumeQuestions` 只送前 6,000 字、`maxOutputTokens` 4096、`timeoutMs` 45,000；schema 照 §5.8.6（15～20 題、三類各 ≥ 3、`text` 5～40 個字且不含中文、`cited_experience` 1～200 字元、正規化後不重複），不合格由 adapter 重試 1 次。
- **AC-T36-2**（§5.1、§5.1.1、§4.21）`POST /resume` 的 body 不合格（路徑不是本人的 `resume/`、副檔名不對、文字是空的、`originalFilename` 清理後是空的或副檔名不是 `.pdf`／`.docx`、`piiRemoved` 缺欄或不是非負整數）→ 400 `validation`，`path` 分別是 `storagePath`、`redactedText`、`originalFilename`、`piiRemoved` 或 `piiRemoved.<欄位>`；都不呼叫 LLM。
- **AC-T36-3**（AC-11、§5.8.1）產生失敗照 §5.0.4 回錯誤，舊 `resume` 列、舊題目都不變；寫一筆 `provider_call`。
- **AC-T36-4**（AC-11、§4.9 第 4 點）成功時 `replace_resume` 在一個交易裡退休舊履歷題、換掉 `resume` 列（`file_name`、`pii_removed` 是這一次的）、寫入新題；函式中任何一步失敗整筆回復（pgTAP）；之後才刪舊原檔，刪失敗不影響回應。
- **AC-T36-5**（AC-12、§4.9 第 4 點）`DELETE /resume` 依序退休 → 刪列 → 刪原檔；第 2 步失敗回 500 `db_failed`，重試能完成；第 3 步失敗回 502 `storage_failed`（可重試，不用 `db_failed`）；沒有履歷回 404；成功回 `{deleted: true}`，`redacted_text` 已不在資料庫。
- **AC-T36-6**（§4.12.1、NFR-04）`resume` bucket 是 private、10 MB；本人只能讀、傳、刪自己資料夾的檔，不能改、不能碰別人的（pgTAP）。
- **AC-T36-7**（`resume.md` §1）還沒上傳、處理中（三步清單與「約 60 秒內」、`beforeunload` 提示）、有履歷（題目依三類分組並顯示題數、每題「引用：{經歷}」、不顯示被問過幾次）、刪除確認（sheet 文字照規格）、刪除完成（綠色狀態列 `role="status"`）五個狀態都照規格。
- **AC-T36-8**（`resume.md` §1）不是 PDF／DOCX →「只能上傳 PDF 或 DOCX」；讀不出文字 →「這個檔案讀不出文字，換一個檔案再試」；上傳到 Storage 失敗（`storage_failed`，可重試）或產生失敗 → 錯誤卡、保留舊履歷與舊題目、可重新上傳；刪除中按鈕「刪除中…」、`disabled`，失敗時 sheet 內「沒有刪除成功，再試一次。」。
- **AC-T36-9**（`resume.md` §1、§4.21；文案**待 Designer**）右欄與設定頁履歷列顯示清理後的原始檔名、上傳日、格式與「移除了幾項」（資料來自 `resume.file_name`、`pii_removed`，跨裝置一致；只列計數 > 0 的類別，都是 0 時寫「沒有找到電話、Email、地址」）；文案照 `resume.md` 現有用字並集中在一個常數檔，Designer 改字不影響邏輯。

- **AC-T36-11**（DESIGN §2、`resume.md`；響應式）手機（< 900px）單欄、右欄內容排在題目清單下方、刪除確認是底部 sheet；電腦（≥ 900px）主欄＋340px 右欄、刪除確認是置中卡；360、412、768、1280、1440 都沒有橫向捲動；按鈕 ≥ 48×48。
