## 目標
使用者錄一段跟讀，`POST /shadow/attempts` 回正確率、語速比、發音分數與是否解鎖，並寫一筆 `shadow_attempt`。一般模式只用 Azure；Azure 沒有給出完整結果就回錯誤、不解鎖、不自動換供應商。「不評分」模式只轉文字、不評分。

## 介面
§4.18 的 `ShadowResultSchema` 照 ARCHITECTURE（contracts 新增 `src/shadow.ts`）；以下是 TechLead 補的決定：
```ts
// packages/contracts/src/shadow.ts（同檔）
export const ShadowAttemptMetaSchema = z.object({ planDate: PlanDateSchema, itemIndex: z.number().int().min(0).max(4) }).strict();   // §4.18.1
export const SHADOW_AUDIO_MAX_BYTES = 1_048_576;   // 1 MiB，§4.18.1
// supabase/functions/api/shadow.ts（新增）；router.ts 的 RouteKey 加 'POST /shadow/attempts'
export const postShadowAttempt: Route;
export const ASSESS_TIMEOUT_MS = 8000;    // 端點目標 ≤ 5 s（§5.1），比照 T-021 的 TTS_TIMEOUT_MS
export const SHADOW_STT_TIMEOUT_MS = 25_000;   // §6 第 6 點的 STT 逾時
// _shared/db/shadow-store.ts（新增；照 user-db.ts）
//   readShadowItem(planDate, itemIndex) → ShadowItem | null（只看 status = 'ready' 的計畫）
//   uploadAudio(path, wav) → null；insertAttempt(row) → null
```
- **請求格式**（§4.18.1，ADR-020 決定 2；Architect 已定）：`multipart/form-data`，只有兩個欄位：`audio`（WAV 檔）與 `meta`（JSON 字串，`ShadowAttemptMetaSchema`）；多出來的欄位忽略。`audio`：先檢查大小 ≤ `SHADOW_AUDIO_MAX_BYTES`，再 `parseWav16kMono`（16 kHz、mono、16-bit、≤ 30 秒）；MIME 有給時只能是 `audio/wav`、`audio/wave`、`audio/x-wav`，沒給也可以；超過、解析失敗或其他 MIME → 400 `validation`、`path` 是 `audio`。`meta`：不是 JSON → `path` 是 `meta`，不合 schema → `meta.<欄位>`；`planDate` 不是台北今天（`toTaipeiPlanDate(deps.now())`）→ 400 `validation`、`path` 是 `meta.planDate`。讀不到 form → 400 `validation`、`path` 是 `body`（§5.1.1）；缺 `audio` → `path` 是 `audio`、缺 `meta` → `meta`。§9.3 的 VAD 只在裝置端算跟唸次數，伺服器不依它收檔。
- **順序**：
  1. 先做上面的全部驗證（含 `meta.planDate` 必須是今天），都不呼叫供應商；通過後 `readShadowItem` → 沒有（計畫不存在、不是 `ready`、或那一句不存在）→ 503 `plan_not_ready`（§5.0.4）。
  2. 參考時長：`ttsObjectPath(userId, voice, normalizeTtsText(item.text))` 的物件（`voice` 照 T-021 的 `readVoice`）→ `find` 有 → `mp3DurationMs(bytes)`；沒有 → 呼叫 `/tts` 同一套「合成＋上傳」（從 `api/tts.ts` 抽成 `_shared/tts/ensure.ts` 的 `ensureTtsAudio`，`postTts` 改用它、行為不變）。合成失敗 → 照 §5.0.4 回那個錯誤。
  3. 讀設定（`SettingsSchema.parse(profile.settings)`）。`pronunciation.scoring` 是 `true` → `resolve('pronunciation', …)` → `assess(wav, stripBreaks(item.text), { timeoutMs: ASSESS_TIMEOUT_MS })`；是 `false` → `resolve('stt', …)` → `transcribe(wav, { language: 'en', wordTimestamps: true, timeoutMs: SHADOW_STT_TIMEOUT_MS })`。`resolve` 的第三個參數是 `sumPaidUsageThisMonthNtd(…)`。
  4. 供應商回 `err`（含缺 `PronScore` 的 `invalid_response`）→ 照 §5.0.4 回錯誤；**不上傳、不寫 `shadow_attempt`、不改用另一個供應商**。
  5. `scoreShadowAttempt(stripBreaks(item.text), durationMs, { recognizedText, words })`（不評分模式的 `words` 來自 `Transcript.words`） → `passed` 就是它的 `unlocked`。
  6. `uploadAudio('<user_id>/shadow/<planDate>/<itemIndex>-<uuid>.wav')`（`crypto.randomUUID()`）→ `insertAttempt`（`pron_score`、`pron_provider` 在「不評分」模式是 null）→ 200＋`ShadowResult`。上傳失敗 → 502 `storage_failed`（`op: 'upload'`，可重試）、不寫列；寫列失敗 → 500 `db_failed`，物件已在 Storage，**不在本單刪除**：沒有 `audio_path` 指到的物件由 T-046 的 `purge-audio` 在建立滿 24 小時後清掉（§4.12.2.1、ADR-020 決定 2）。
- **`provider_call`**：每次 `assess`、`transcribe`（以及第 2 步真的合成時的 `synthesize`）不論成敗都用 `userDb.insertProviderCall` 寫一筆；寫入失敗只記 log，不影響回應。
- **已由 ARCH v1.14 定案的邊界**（QA 的待釐清 A8、A10、A12～A14 照這裡）：
  - `meta.planDate` 不是台北今天（昨天、明天都是）：一律 400 `validation`、`path` 是 `meta.planDate`，發生在 `readShadowItem` 之前，所以計畫沒好也是 400、不是 503（§4.18.1 失敗表「驗證失敗」）。
  - 讀 TTS 快取時 Storage 讀取失敗：502 `storage_failed`（`op: 'download'`，可重試），不合成、不評分（§5.0.4 的 `storage_failed` 說明：Storage 錯誤一律用這個 kind）。
  - `SettingsSchema.parse(profile.settings)` 失敗：500 `internal`，不改用預設值（§4.15.1「讀」）。
  - 「不評分」模式：`wordTimestamps: true` 時 STT 保證 `timing: 'words'`，回 `timing: 'none'` 就當 `invalid_response`（502，§5.0.7）；`text` 空且 `words` 空（整段沒講話）是 `ok`，`accuracy` 0、`speedRatio` 0、`passed: false`，照樣上傳、寫列（§5.7.3）；`text` 有內容但 `words` 空由 adapter 回 `invalid_response`（§5.7.3）。語速比 0 只在沒有任何有聲時間時出現，這時正確率也是 0，本來就不能解鎖；解鎖規則只有一條：正確率 ≥ 0.8 且語速比 ≥ 0.7（§4.6），不另設例外。
  - `resolve` 本身失敗（`paid_not_allowed`、`not_configured` 等）：沒有外部呼叫，所以不寫 `provider_call`（§4.18.1：寫的是 assess／transcribe／synthesize 的呼叫），回該錯誤；供應商 0 次。
- **待 Architect**（不擋派工；下面的暫定規則照寫，Architect 回覆後只改該規則與對應的測試）：
  - Q-T30-a（AC-T30-4）一般模式的 `meta.sttProvider` 與 `shadow_attempt.stt_provider`（`not null`）填什麼：ARCH §4.18 只規定 `meta.pronProvider`。暫定：填和 `pronProvider` 同一個 Azure 供應商 id，因為辨識文字與逐字時間來自 Azure。
  - Q-T30-b（AC-T30-11）時長 0（0 個取樣的 WAV）：`parseWav16kMono` 會通過。暫定：handler 在解析後檢查 `durationMs > 0`，否則 400 `validation`、`path` 是 `audio`；請 Architect 把「時長 > 0」寫進 §4.18.1。
  - Q-T30-c（AC-T30-11）檔頭少報 data 大小（宣告 1 秒、實際 31 秒）：parser 只量宣告值。暫定：送去供應商與上傳的是請求原本的位元組，由 1 MiB 上限擋住最壞情況；請 Architect 決定要不要只取宣告長度內的位元組，或讓 parser 檢查檔案長度與宣告一致（`audio.ts` 不在本單範圍）。
  - Q-T30-d（AC-T30-1、AC-T30-11）multipart 細節：MIME 比對不分大小寫、忽略 `;` 後面的參數；`audio` 不是檔案 → 400 `audio`；`meta` 不是字串 → 400 `meta`；同名欄位重複取第一個；`meta` 多出的鍵 → 400、`path` 是 `meta`；`audio` 與 `meta` 都不合格時兩個 issue 都回（`audio` 在前）。這些都是暫定。
  - Q-T30-e（AC-T30-3）TTS 快取物件是 0 位元組（參考時長 0，`scoreShadowAttempt` 會回 `validation`）：暫定當成沒有快取、重新合成並覆寫。
- **`RouteDeps`** 加必填 `shadowStore: (ctx: AuthContext) => ShadowStore`；`makeTestRouteDeps` 同一個 commit 補預設值，並新增 `makeTestShadowStore`（`_shared/db/test/fakes.ts`，沒覆寫的方法回 `not stubbed: <名稱>`）（§5.1.1 規則 2、3）。

## 限制
- 不加依賴；根目錄 `package.json` 與 `.dependency-cruiser.cjs` 不動，所以 `tooling/o010.test.mjs`（TC-15）、`tooling/arch-rules.test.ts`（TC-24）不在範圍內。

- `user_id` 一律取自 `AuthContext`；body 帶的任何 id 都不採用。錄音只經本端點上傳（§4.12.1「Azure 金鑰不下發」）。
