## 目標
使用者錄一段跟讀，`POST /shadow/attempts` 回正確率、語速比、發音分數與是否解鎖，並寫一筆 `shadow_attempt`。一般模式只用 Azure；Azure 沒有給出完整結果就回錯誤、不解鎖、不自動換供應商。「不評分」模式只轉文字、不評分。錄音先照 §4.18.1 驗證並正規化，送出與存檔的都是同一份正規化 WAV。

## 介面
§4.18 的 `ShadowResultSchema`、§4.18.1 的 `ShadowAttemptMetaSchema` 照 ARCHITECTURE（contracts 新增 `src/shadow.ts`）；§5.0.5 的音訊常數與 `parseWav16kMono` 放 `src/audio.ts`，`shadow.ts` 不另定義（C6）。以下是 TechLead 補的決定：
```ts
// packages/contracts/src/audio.ts：常數照 §5.0.5（MAX_BYTES、MIN／MAX_DURATION_MS、MIN／MAX_DATA_BYTES）
export function parseWav16kMono(bytes: Uint8Array, maxDurationMs?: number, minDurationMs?: number): Result<Wav16kMono, ValidationError>;
// supabase/functions/api/shadow.ts（新增）；router.ts 的 RouteKey 加 'POST /shadow/attempts'
export const postShadowAttempt: Route;
export const ASSESS_TIMEOUT_MS = 8000;          // 端點目標 ≤ 5 s（§5.1）
export const SHADOW_STT_TIMEOUT_MS = 25_000;    // §6 第 6 點
// _shared/db/shadow-store.ts（新增；照 user-db.ts）
//   readShadowItem(planDate, itemIndex) → ShadowItem | null（只看 status = 'ready' 的計畫）
//   uploadAudio(path, wav) → null；insertAttempt(row) → null
```
- **multipart**（§4.18.1）：只認 `audio`（檔案）與 `meta`（JSON 字串），其他名稱的欄位忽略。讀不到 form → 400 `validation`、`path` 是 `body`；缺 `audio` → `audio`、缺 `meta` → `meta`；同名欄位出現兩次以上 → 400、`path` 是該欄位名（不取第一個或最後一個）；`audio` 不是檔案 → `audio`；`meta` 不是字串或不是合法 JSON → `meta`；schema 錯 → `meta.<欄位>`，`.strict()` 擋下的多餘鍵 → `meta.<key>`（例：`meta.userId`）；`audio` 與 `meta` 都不合格 → 一次 400、兩個 issue（`audio` 在前）（C5）。
- **音訊**（§4.18.1、§5.0.5；C1～C4、C6）：先量整份 buffer，> `SHADOW_AUDIO_MAX_BYTES` → 400 `audio`，不呼叫 parser。MIME 有給時比對 type／subtype（不分大小寫、忽略 `;` 後參數），只收 `audio/wav`、`audio/wave`、`audio/x-wav`；沒給也可以。parser 規則照 §4.18.1：只收一種 PCM（`fmt ` 在 `data` 前、`audioFormat` 1、16 kHz、mono、16-bit LE、`blockAlign` 2、`byteRate` 32_000）；依 RIFF 逐個走 chunk，其他合法 chunk 不論位置都忽略；chunk id 四個位元組是 `0x20`–`0x7E` 且第一個不是空白；`dataBytes` 取宣告大小，超出檔尾或是奇數 → 400；檔尾例外只容許最後一個奇數 chunk 省略 padding；無法解析的尾巴 → 400。門檻比的是 `dataBytes`：`< 9_600` 或 `> 960_000` → 400（9_584、960_002 都擋），毫秒常數 300、30_000 保留。parser 預設下限 0；handler 呼叫時傳 `SHADOW_AUDIO_MAX_DURATION_MS` 與 `SHADOW_AUDIO_MIN_DURATION_MS`（只傳這兩個整數常數）。毫秒參數必須是非負整數且 `minDurationMs <= maxDurationMs`，否則回 `err`（`ValidationError`），不丟例外（P3，ARCH v1.17）。參數檢查在解析 WAV 之前（ARCH v1.18，P4）：任一參數不合格就不看 WAV；每個不合格參數各一條 issue，path 是 `minDurationMs` 或 `maxDurationMs`，先 min 後 max；兩個各自合格但 `minDurationMs > maxDurationMs` 時只回一條，path 是 `minDurationMs`。回傳的 `Wav16kMono.bytes` 是只含 RIFF／`fmt `／`data` 的正規化 WAV，大小欄與實際 data 一致；送 Azure、送 STT、寫 Storage 都用它（C4）。
- **`0xFFFFFFFF`**：宣告為 `0xFFFFFFFF` 時 `data` 到檔尾，剩餘位元組必須是 2 的倍數（v1.16）；後面接的位元組一律算音訊、不解析成 chunk，計入門檻並進正規化輸出（P2，ARCH v1.17）。
- **順序**（§4.18.1「處理順序」）：
  1. 全部驗證（含 `meta.planDate` 必須是 `toTaipeiPlanDate(deps.now())`，不是 → 400 `meta.planDate`）都在讀計畫之前、都不呼叫供應商；通過後 `readShadowItem` → 沒有 → 503 `plan_not_ready`。
  2. 讀設定：`SettingsSchema.parse(profile.settings)` 失敗 → 500 `internal`，不換預設值。
  3. 參考時長：`ttsObjectPath(userId, voice, normalizeTtsText(item.text))` → `find` 有且 > 0 位元組 → `mp3DurationMs(bytes)`；不存在或 0 位元組 → `ensureTtsAudio`（從 `api/tts.ts` 抽到 `_shared/tts/ensure.ts`，`postTts` 改用它、行為不變）合成並覆寫；`find` 回 Storage 錯誤 → 502 `storage_failed`（`op: 'download'`），不合成。合成失敗照 §5.0.4。
  4. `scoring: true` → `resolve('pronunciation', …)` → `assess(wav, stripBreaks(item.text), { timeoutMs: ASSESS_TIMEOUT_MS })`；`scoring: false` → `resolve('stt', …)` → `transcribe(wav, { language: 'en', wordTimestamps: true, timeoutMs: SHADOW_STT_TIMEOUT_MS })`。
  5. 供應商 `err`（含缺 `PronScore` 的 `invalid_response`）→ 照 §5.0.4；不上傳、不寫列、不換供應商。
  6. `scoreShadowAttempt(stripBreaks(item.text), durationMs, { recognizedText, words })` → `passed` 是它的 `unlocked`。
  7. `uploadAudio('<user_id>/shadow/<planDate>/<itemIndex>-<uuid>.wav')` → `insertAttempt` → 200＋`ShadowResult`。上傳失敗 → 502 `storage_failed`（`op: 'upload'`）、不寫列；寫列失敗 → 500 `db_failed`，不刪物件（T-046 的 `purge-audio` 清，§4.12.2.1）。
- **已定案的規則**（原 Q-T30-a～e，§4.18.1 處理順序 3～6）：一般模式的 `meta.sttProvider`、`shadow_attempt.stt_provider`、`meta.pronProvider` 都是這次發音評估的供應商 id；「不評分」模式 `timing` 不是 `'words'`、或文字非空卻沒有逐字時間 → 502 `invalid_response`、不上傳；文字與 `words` 都空 → 200、`accuracy` 0、`speedRatio` 0、`passed: false`、照樣上傳寫列；`resolve` 本身失敗不寫 `provider_call`；0 位元組快取當未命中（上面第 3 步）。
- **`provider_call`**：每次 `assess`、`transcribe`、真的合成時的 `synthesize` 不論成敗各寫一筆；寫入失敗只記 log。
- **`RouteDeps`** 加必填 `shadowStore: (ctx: AuthContext) => ShadowStore`；`makeTestRouteDeps` 同一個 commit 補預設值，並新增 `makeTestShadowStore`（沒覆寫的方法回 `not stubbed: <名稱>`）（§5.1.1）。

## 驗收標準
- **AC-T30-1**（§4.18.1、§5.1.1）multipart 照「介面」：多的欄位忽略；form 讀不到（`body`）、缺 `audio`、缺 `meta`、同名欄位重複（該欄位名）、`audio` 不是檔案、`meta` 不是字串或不是 JSON（`meta`）、`itemIndex` 不在 0～4、`planDate` 格式錯或不是台北今天（`meta.planDate`，計畫有沒有好都一樣）、多餘鍵（`meta.<key>`）：400 `validation`；兩者都不合格時兩個 issue、`audio` 在前；全部不呼叫供應商、不讀計畫。
- **AC-T30-2**（§5.0.4）計畫不存在、不是 `ready`、或那一句不存在：503 `plan_not_ready`；不呼叫供應商。
- **AC-T30-3**（§4.6、§4.19、§4.18.1 順序 3）參考時長來自 TTS 快取物件（`mp3DurationMs`）；不存在或 0 位元組時用 `ensureTtsAudio` 合成並覆寫後再評分；合成失敗照 §5.0.4、不評分；讀快取時 Storage 失敗回 502 `storage_failed`（`op: 'download'`）、不合成；`postTts` 改用 `ensureTtsAudio` 後行為不變（T-021 的測試照樣通過）。
- **AC-T30-4**（§4.18、§4.18.1 順序 4）`scoring` 是 `true`：只呼叫 `assess`（參考文字已去掉「/」、`timeoutMs` 8,000），STT 0 次；回 `scoring: 'azure'`、`pronScore` 是 Azure 的分數；`meta.pronProvider`、`meta.sttProvider`、寫入的 `stt_provider` 都是發音評估的供應商 id。
- **AC-T30-5**（§4.18、ADR-018 決定 9、ADR-003）`assess` 回任何 `err`（429、5xx、逾時、未設定、缺 `PronScore` 的 `invalid_response`）：照 §5.0.4；STT 0 次、不上傳、不寫 `shadow_attempt`。
- **AC-T30-6**（§4.18「不評分」、§4.18.1 順序 5）`scoring` 是 `false`：只呼叫 `transcribe`（`wordTimestamps: true`、`timeoutMs` 25,000），發音評估 0 次；回 `scoring: 'off'`、`pronScore: null`、`meta.pronProvider: null`；STT 失敗同 AC-T30-5；`timing` 不是 `'words'`、或文字非空卻沒有逐字時間 → 502 `invalid_response`、不上傳；文字與 `words` 都空 → 200、`accuracy` 0、`speedRatio` 0、`passed: false`，照樣上傳、寫列；`stt_provider` 是設定的 STT 供應商。
- **AC-T30-7**（§4.6、AC-06）`accuracy`、`speedRatio` 等於 `scoreShadowAttempt` 的結果；`passed` 只看正確率 ≥ 0.8 且語速比 ≥ 0.7，發音分數不影響。
- **AC-T30-8**（§4.12.1、§4.18）成功時正規化 WAV 上傳到 `audio` bucket 的 `<user_id>/shadow/<planDate>/<itemIndex>-<uuid>.wav`，再寫一筆 `shadow_attempt`（欄位照 T-006 的 `grant insert` 清單、`user_id` 取自 `AuthContext`）；上傳失敗 502 `storage_failed`（可重試）、不寫列；寫列失敗 500 `db_failed`，不刪已上傳的物件。
- **AC-T30-9**（§13、§4.18.1 順序 6）每次外部呼叫寫一筆 `provider_call`（成功 `errorKind` 是 null、失敗是那個 kind）；寫入失敗不影響回應；`resolve` 失敗、驗證失敗、快取命中都不寫列。
- **AC-T30-10**（§5.1.1、§4.15.6、§4.18.1 順序 2）`RouteDeps.shadowStore` 必填、`makeTestShadowStore` 沒覆寫的方法回 `not stubbed:`；`resolve` 的第三個參數是 `sumPaidUsageThisMonthNtd` 的結果；`profile.settings` 解析失敗回 500 `internal`；log 不含辨識文字、原句與路徑。
- **AC-T30-11**（§4.18.1、§5.0.5）大小、MIME、格式，錯誤一律 400 `validation`、`path` 是 `audio`、供應商 0 次：① 1,048,576 位元組進解析，1,048,577 位元組直接擋、parser 0 次；② MIME 只收三種（不分大小寫、忽略參數，`audio/WAV`、`audio/wav; codecs=1` 通過），沒給也可以，`audio/mpeg`、`audio/webm` 擋；③ 不是 16 kHz、mono、16-bit LE 整數 PCM（含 IEEE float、extensible、`blockAlign` 或 `byteRate` 不符、`fmt ` 在 `data` 之後、檔名 `.wav` 但內容不是）擋。
- **AC-T30-12**（§4.18.1 chunk 規則、ADR-021 修訂 2 N1、N5～N7）parser：① `fmt ` 前、兩者之間、`data` 後的合法 chunk（`LIST`、`JUNK`）忽略、不計時長、不進輸出；② id 不是可印 ASCII 或首字元是空白（`\0\0\0\0`、四個空白，含少報 `data` 大小後接全 0 或非 0 取樣的尾巴）→ 400；③ 宣告大小超出檔尾或是奇數 → 400；④ 最後一個奇數 chunk 剛好在檔尾省略 padding → 通過，padding 缺失但後面還有位元組、標頭不完整的尾巴 → 400；⑤ `0xFFFFFFFF`：到檔尾，剩餘是奇數 → 400，後面接合法 `LIST` 時那些位元組算音訊（P2，ARCH v1.17）。
- **AC-T30-13**（§4.18.1 時長門檻、§5.0.5、ADR-021 修訂 2 N2、N3）門檻比 `dataBytes`：9_600 與 960_000 通過，9_584、960_002、0 個取樣 → 400；`parseWav16kMono` 預設下限 0（10 ms 的 WAV 用預設參數仍是 `ok`），上限預設 30_000；handler 傳 300 ms 下限；參數不合格（`299.5`、`NaN`、負數、下限大於上限）→ 回 `err`、不丟例外（P3，ARCH v1.17；path 與檢查順序見 AC-T30-15，ARCH v1.18）；`SHADOW_AUDIO_*` 常數只在 `audio.ts` 定義一次並從 contracts 匯出，`shadow.ts` 與 handler 不重複定義；既有 `audio.test.ts` 只有一個截斷測試（名稱 `UNDECIDED: a data chunk larger than the file is clamped to the bytes that exist`），改成預期 400；同檔另外兩個 UNDECIDED（30 s 上限含等於、拒收 `WAVE_FORMAT_EXTENSIBLE`／`0xFFFE`）維持原預期，不改。
- **AC-T30-14**（§4.18.1 正規化輸出、ADR-021 決定 1）`Wav16kMono.bytes` 只含 RIFF／`fmt `／`data`，RIFF 與 `data` 的大小欄等於實際長度；`assess`、`transcribe` 收到的與 `uploadAudio` 寫入的是同一份正規化位元組，不是請求原本的位元組；被忽略的 chunk 與少報大小後的尾巴不會送出。
- **AC-T30-15**（§4.18.1、§5.0.5，ARCH v1.18，P4）`parseWav16kMono` 先檢查參數、再解析 WAV。任一參數不合格（非整數、負數、`NaN`、`Infinity` 等）即回 `err`（`ValidationError`），不看 WAV 內容。每個不合格參數各一條 issue，path 是 `minDurationMs` 或 `maxDurationMs`，先 min 後 max。兩個各自合格但 `minDurationMs > maxDurationMs` 時只回一條 issue，path 是 `minDurationMs`。不丟例外。
