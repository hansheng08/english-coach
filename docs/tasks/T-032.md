## 目標
新增 `POST /reviews`：驗證請求、讀卡與 `settings.srs`、用 `applyReview` 在 TypeScript 算新排程，再呼叫 SQL 函式 `record_card_review` 在同一個交易裡比對舊值、更新 `card`、寫一筆 `card_review`；同一張卡同一個台北日期只能評一次，由資料庫的唯一約束保證。回傳更新後的 `Card`。

// supabase/functions/_shared/db/test/fakes.ts（新增；測試程式，§5.1.1 工廠函式表）
export function makeTestDbClient(overrides?: { readonly from?: (table: string) => Partial<ReturnType<DbClient['from']>> }): DbClient;

- **工廠函式的預設值**（§5.1.1 表）：沒覆寫的方法一律回錯誤，不默默通過——`DbClient` 的 `from(<表>).insert` 回 `{ data: null, error: { code: 'TEST', message: 'not stubbed: <表>.insert' } }`；`UserDb` 每個方法回 `err({ kind: 'internal', message: 'not stubbed: <名稱>' })`。`makeTestRouteDeps`：`userDb` 是 `() => makeTestUserDb()`、`now` 固定回 `2026-11-27T00:00:00Z`；`reviewDb` **預設不給**（暫時選填，TC-18 就是不給的情況）。`makeTestRouterDeps`：`auth` 是 `ok`、`verifyToken` 對任何 token 回同一個固定的測試使用者；`routeDeps` 是 `ok(makeTestRouteDeps())`；`allowedOrigins` 一個測試 origin；`keyPresence` 四個都是 `true`、`onlyLegacyKeys` 是 `false`；`log` 不輸出。覆寫的值直接取代預設值（淺層合併）。
- 回傳型別一律是完整的介面，所以之後任何單在這四個介面加必填欄位卻沒補預設值，是**工廠函式**編譯失敗，不是測試檔。
- `ReviewDbClient`：`reviews.ts` 內的最小介面，只含這張單用到的 supabase-js 方法（讀一列、`rpc`）；`createUserClient` 的回傳型別改成同時滿足既有 `DbClient` 與 `ReviewDbClient`，既有的假 client 不必改。
- **依賴的接法（v1.2）**：§5.1.1 規定新依賴加在 `RouteDeps`，欄位名稱由第一張用到的單定，本單定為 `reviewDb`。它**暫時**是選填欄位（§5.1.1 過渡第 1 步）：QA 探針還寫死完整的 `RouteDeps`，加必填欄位會讓 `tsc -b` 失敗；QA 改完探針、合併後，T-025a 把它改回必填並刪掉「沒接」的判斷。`index.ts` 一律接上 `reviewDb: (ctx) => createReviewDb(ctx, env)`（`env` 和 `userDb` 用同一個 `loadSupabaseEnv` 結果）。`deps.reviewDb` 沒接時回 500 `internal`（`message: 'reviewDb not wired'`），不讀卡。
- **處理順序**（`postReviews`，依賴只從 `RouteDeps` 拿：`deps.reviewDb(ctx)`、`deps.now()`；不呼叫 `deps.userDb`）：
  1. body 照 §5.1.1 驗證，用 `ReviewRequestSchema`。
  2. `readCardForReview`；`null` → 404 `not_found`（`entity: 'card'`）。
  3. `readSrsSettings`：`profile` 列不存在或 `settings` 沒有 `srs` → `SrsSettingsSchema.parse({})` 的預設值；有 `srs` 但不符合 schema → 500 `internal`（不默默改用預設）。
  4. `today = toTaipeiPlanDate(deps.now())`；`applyReview(card.schedule, rating, today, srs)`；`err`（Mastered）→ 400 `validation`。
  5. `recordCardReview({ cardId, reviewDate: today, mode, rating, before: card.schedule, outcome })`。
  6. 成功 → 200，body 是 `CardSchema` 的值：讀到的卡片欄位＋回傳的新 `schedule`。
- `recordCardReview` 呼叫 `record_card_review`，參數依 §4.11 的順序對應（`p_expected_*` 是讀到的舊值，`p_new_*` 是 `outcome.schedule`，`p_interval_days_applied` 是 `outcome.intervalDaysApplied`）。錯誤碼 `23505`、`40001` → `conflict`（`entity: 'card'`，409）；`P0002` → `not_found`（`entity: 'card'`）；其他 → `db_failed`（訊息格式同 `runDb`，不含任何值）。
- **migration**（一個檔，`supabase/migrations/<時間戳記>_t032_card_review_date_record_review.sql`；時間戳記取寫檔時的台北時間，必須比 `supabase/migrations/` 最新的檔案晚；ARCH §4.11 已定義這個 migration 的內容，本單照寫、不另外設計）：依 §4.11 的順序加 `review_date`（回填、`not null`、`card_review_card_id_review_date_key`），**不加 `default`**（§4.11 沒有；以前的草稿為了讓 `t004_rls_test.sql` 不改也能過而加 `default`，本版改成修改那個 pgTAP 的 fixture，見下一點）；建立 `record_card_review`（`security invoker`、`set search_path = ''`、函式內 6 步照 §4.11）；`revoke`／`grant` 照 §4.11 的兩行。
- **既有 pgTAP 要跟著改**：`not null` 且沒有預設值之後，`supabase/tests/t004_rls_test.sql` 裡所有 `insert into public.card_review` 都要補 `review_date`（fixture 一筆、AC-T4-6 的四筆）：每一筆用不同的日期（例如 fixture 用 `2026-11-20`，A 的合法那筆用 `2026-11-21`，其餘依序往後），這樣 `card_review_card_id_review_date_key` 不會在原本期待的錯誤碼（`23503`、`42501`、`23514`）之前先觸發；只加欄位與值，斷言、名稱、期待的錯誤碼都不改。

## 測試的寫法
- 端點測試經 `createRouter(makeTestRouterDeps({ routeDeps: ok(makeTestRouteDeps({ reviewDb: … })) }))` 送 `Request`（`/api/reviews`），`reviewDb` 給假 `ReviewDb`；`userDb` 用預設的 `makeTestUserDb()`（被呼叫就會回錯，TC-1、TC-18 的「0 次」用覆寫的記錄函式檢查）；`now` 回固定 `Date`；不讀系統時鐘，不寫任何固定等待。
- repository 測試給假 `ReviewDbClient`（記錄 `rpc` 名稱與參數、回設定好的 `{ data, error }`）；不連網、不連資料庫。
- pgTAP 放 `supabase/tests/t032_record_card_review_test.sql`，寫法照 `t004_rls_test.sql`（切換 `authenticated` 身分、`throws_ok` 比對錯誤碼）；本機不能跑，由 PR CI 的 `db` job 驗證。
