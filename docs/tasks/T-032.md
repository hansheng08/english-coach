## 目標
新增 `POST /reviews`：驗證請求、讀卡與 `settings.srs`、用 `applyReview` 在 TypeScript 算新排程，再呼叫 SQL 函式 `record_card_review` 在同一個交易裡比對舊值、更新 `card`、寫一筆 `card_review`；同一張卡同一個台北日期只能評一次，由資料庫的唯一約束保證。回傳更新後的 `Card`。

## 介面
TechLead 決定（§4.11 已定的名稱照 §4.11；其餘照此）：
```ts
// packages/contracts/src/card.ts（新增；camelCase，對應 card 表除了 user_id、seed_chunk_id 以外的欄位）
export const CardSchema = z.object({ id: CardIdSchema, chunk: z.string(), meaningZh: z.string().nullable(), exampleEn: z.string().nullable(),
  synonyms: z.array(z.string()), sourceSentence: z.string().nullable(), sourceType: CardSourceTypeSchema, schedule: CardScheduleSchema,
  priorityNew: z.boolean(), ttsPath: StoragePathSchema.nullable(), generatedBy: z.string().nullable(),
  createdAt: z.iso.datetime({ offset: true }), masteredAt: z.iso.datetime({ offset: true }).nullable() });
// supabase/functions/_shared/db/reviews.ts（新增）：RecordReviewInput、recordCardReview 照 §4.11，另加
export function readCardForReview(client: ReviewDbClient, cardId: CardId): Promise<Result<Card | null, AppError>>;
export function readSrsSettings(client: ReviewDbClient, userId: UserId): Promise<Result<SrsSettings, AppError>>;
// user-db.ts 的 UserDb 新增 readCardForReview、readSrsSettings（不帶 client／userId）、recordCardReview（§4.11）
// supabase/functions/api/reviews.ts（新增）
export const postReviews: Route;   // router.ts 的 RouteKey 加 'POST /reviews'
```
- `ReviewDbClient`：`reviews.ts` 內的最小介面，只含這張單用到的 supabase-js 方法（讀一列、`rpc`）；`createUserClient` 的回傳型別改成同時滿足既有 `DbClient` 與 `ReviewDbClient`，既有的假 client 不必改。
- **處理順序**（`postReviews`，依賴只從 `RouteDeps` 拿：`deps.userDb(ctx)`、`deps.now()`，不加新欄位）：
  1. body 照 §5.1.1 驗證，用 `ReviewRequestSchema`。
  2. `readCardForReview`；`null` → 404 `not_found`（`entity: 'card'`）。
  3. `readSrsSettings`：`profile` 列不存在或 `settings` 沒有 `srs` → `SrsSettingsSchema.parse({})` 的預設值；有 `srs` 但不符合 schema → 500 `internal`（不默默改用預設）。
  4. `today = toTaipeiPlanDate(deps.now())`；`applyReview(card.schedule, rating, today, srs)`；`err`（Mastered）→ 400 `validation`。
  5. `recordCardReview({ cardId, reviewDate: today, mode, rating, before: card.schedule, outcome })`。
  6. 成功 → 200，body 是 `CardSchema` 的值：讀到的卡片欄位＋回傳的新 `schedule`。
- `recordCardReview` 呼叫 `record_card_review`，參數依 §4.11 的順序對應（`p_expected_*` 是讀到的舊值，`p_new_*` 是 `outcome.schedule`，`p_interval_days_applied` 是 `outcome.intervalDaysApplied`）。錯誤碼 `23505`、`40001` → `conflict`（`entity: 'card'`，409）；`P0002` → `not_found`（`entity: 'card'`）；其他 → `db_failed`（訊息格式同 `runDb`，不含任何值）。
- **migration**（一個檔，`supabase/migrations/<時間戳記>_t032_card_review_date_record_review.sql`；時間戳記取寫檔時的台北時間，必須比 `supabase/migrations/` 最新的檔案晚）：依 §4.11 的順序加 `review_date`（回填、`not null`、`card_review_card_id_review_date_key`）；建立 `record_card_review`（`security invoker`、`set search_path = ''`、函式內 6 步照 §4.11）；`revoke`／`grant` 照 §4.11 的兩行。

## 驗收標準
- **AC-T32-1**（§5.1）`ROUTES` 有 `POST /reviews`；沒有 token、token 無效 → 401 `unauthenticated`，不呼叫 `userDb`。
- **AC-T32-2**（§5.1.1 body 驗證）body 不是 JSON → 400 `validation`（`path: 'body'`）；不符合 `ReviewRequestSchema` → 400 `validation`，`path` 是 zod issue 的路徑；都不讀卡。
- **AC-T32-3**（§4.11 第 2 步）卡片讀不到（不存在或不是本人的）→ 404 `not_found`（`entity: 'card'`），不呼叫 `recordCardReview`。
- **AC-T32-4**（§4.11 第 3 步、§4.2）沒有 `profile` 列、`settings` 沒有 `srs` 時用 `SrsSettingsSchema` 預設值；有自訂 `srs` 時用它算（`interval_days_applied` 跟著變）；`srs` 不合法 → 500 `internal`。
- **AC-T32-5**（§4.11 第 4、5 步、§4.3）`today` 是 `deps.now()` 換算的台北日期（午夜前後各一秒正確）；Mastered 卡 → 400 `validation`，不呼叫 `recordCardReview`。
- **AC-T32-6**（§4.11 SQL 函式參數）`recordCardReview` 呼叫 `record_card_review` 一次，13 個參數的值照「介面」對應（舊值四欄、新值四欄、`p_review_date`、`p_mode`、`p_rating`、`p_interval_days_applied`）。
- **AC-T32-7**（§5.1、本單 `CardSchema`）成功 → 200，body 通過 `CardSchema`，`schedule` 是新排程、其他欄位是讀到的值；`CardSchema` 拒絕缺欄位、`schedule` 不合法（例如 mastered 卻有 `dueDate`）的值。
- **AC-T32-8**（§4.11 錯誤對應）`23505`、`40001` → 409 `conflict`（`entity: 'card'`）；`P0002` → 404 `not_found`；其他錯誤碼或 supabase-js 丟例外 → 500 `db_failed`；`message` 不含卡片內容與排程值。
- **AC-T32-9**（§4.11 migration，靜態檢查）migration 原文：`review_date date` 的新增、回填（`at time zone 'Asia/Taipei'`）、`set not null`、唯一約束名稱照 §4.11；`record_card_review` 的參數型別順序、`security invoker`、`set search_path = ''`、`returns public.card`；`revoke … from public, anon` 與 `grant execute … to authenticated` 兩行的參數型別清單相同。
- **AC-T32-10**（§4.11 pgTAP；由 PR CI 驗證）`authenticated` 呼叫 `record_card_review`：正常一次 → `card` 更新、`card_review` 多一列且 `review_date` 正確；同一卡同一 `review_date` 第二次 → `23505` 且 `card` 不變；舊值不符 → `40001` 且兩張表都不變；`p_review_date` 不是台北今天 → `40001`；別人的卡 → `P0002`；`authenticated` 直接 `insert card_review` 同卡同日兩次 → 第二次 `23505`；`anon` 不能執行函式。

## 測試的寫法
- 端點測試經 `createRouter` 送 `Request`（`/api/reviews`），`RouteDeps.userDb` 給假 `UserDb`、`now` 回固定 `Date`；不讀系統時鐘，不寫任何固定等待。
- repository 測試給假 `ReviewDbClient`（記錄 `rpc` 名稱與參數、回設定好的 `{ data, error }`）；不連網、不連資料庫。
- pgTAP 放 `supabase/tests/t032_record_card_review_test.sql`，寫法照 `t004_rls_test.sql`（切換 `authenticated` 身分、`throws_ok` 比對錯誤碼）；本機不能跑，由 PR CI 的 `db` job 驗證。
