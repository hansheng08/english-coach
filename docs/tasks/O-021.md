## 背景（開始前先讀）
- main 分支保護的必過 contexts 是 `ci-ok` 與 `g3-comment-guard`。`.github/scripts/g3-comment-guard.sh` 在標題不是 `[G3]` 開頭時印 `title does not start with [G3]; not checked` 後直接 exit 0，且當時尚未把 `HEAD_SHA` 設成 PR 的 `head.sha`，因此不寫 commit status。
- 寫單當下用 REST 讀三個 PR 的 combined status，都是 `state=pending`、`statuses=[]`、`total_count=0`（沒有 `g3-comment-guard` 這筆 status）。workflow run 本身是 success，例如 #52 最新 [run 45810588761](https://github.com/hansheng08/english-coach/actions/runs/45810588761) 的 log 有上述那行。同 head 的 `ci-ok` job 是 success（#52 [run 45810525604](https://github.com/hansheng08/english-coach/actions/runs/45810525604)、#53 [run 45810027553](https://github.com/hansheng08/english-coach/actions/runs/45810027553)、#54 [run 45809052955](https://github.com/hansheng08/english-coach/actions/runs/45809052955)）。check-runs 與 GraphQL `statusCheckRollup` 回 403，原文見文末「權限被拒」。
- 現行 workflow（`.github/workflows/g3-comment-guard.yml`）的 `pull_request` types 已包含 `opened`、`edited`、`reopened`、`synchronize`，另有 `issue_comment`（created／edited）、`pull_request_review`（submitted／edited）、`pull_request_review_comment`（created／edited）。標題變更已會重跑；缺的是非 [G3] 路徑要寫 status。本單**不需要改 workflow 觸發條件**。依憲章 v7 §5，`.github/workflows/` 與 `.github/` 下的 CI 腳本由 SRE 接線，不是 Claude Code。
- 既有測試 `.github/scripts/g3-comment-guard-test.sh` 用 `GH_BIN` 假 gh，只斷言 exit code 與寫入的 `state`；其中案例 `non-G3 PR is not checked: exit 0, no status` 必須改成符合新行為，不得刪掉這條覆蓋。

## 目標
讓標題不是 `[G3]` 開頭的 PR 也在 head SHA 寫入 `g3-comment-guard` 的 success status，必過檢查不會永遠 Waiting；標題在 `[G3]` 與非 `[G3]` 之間變更時，status 要跟著更新。`[G3]` 的留言檢查與 fail-closed 維持不變。

## 介面
腳本仍由 workflow 以環境變數 `GH_TOKEN`、`REPO`、`PR_NUMBER`、`RUN_URL` 呼叫（測試可注入 `GH_BIN`、`TOOLING_DIR`）。Commit status 的 `context` 仍為 `g3-comment-guard`，目標 URL 仍為 `RUN_URL`。寫入時的 SHA 只能是 PR JSON 的 `head.sha`（40 位小寫十六進位），不得使用 merge SHA 或 `GITHUB_SHA`。

### 狀態規則
- 先讀 PR、核對 `head.sha`，再依標題分支。標題讀不到但 SHA 已核對時，寫 failure status 再 exit 非 0。
- 標題以 `[G3]` 開頭：行為與現況相同（讀三種留言、跑 `tooling/comment-lint.mjs`，依結果寫 success 或 failure）。
- 標題不是 `[G3]` 開頭：不讀留言、不跑 comment-lint；在 head SHA 寫 `state=success`、`description` 必須恰好是 `not a [G3] PR; not checked`，然後 exit 0。
- 寫入 status 失敗：exit 非 0。若 head SHA 已知，還要嘗試寫 failure status；不得在沒寫成 success 時 exit 0。
- 讀不到 PR、標題或 `head.sha`，或 SHA 格式不符：exit 非 0。SHA 未知時不要寫 status。
- 不得新增未註明理由的 `|| true` 或 `continue-on-error`。

### 標題變更（workflow 已有 `edited`）
同一腳本每次都依當下標題重寫 status，即可覆蓋兩個方向：非 [G3] 改成 `[G3]` 開頭後跑真正檢查並更新 status；`[G3]` 改成非 [G3] 後改寫成上面那句 not-checked success。不需改 `.github/workflows/g3-comment-guard.yml`。若實作後發現觸發條件其實不夠，停下寫進報告，由 SRE 接線，不要自行改 workflow。

### 已卡住的 PR（只說明，不要操作）
實作合併進 main 之後，#52、#53、#54 不會自動出現新 status，需要再觸發一次：改標題（例如加減結尾空白，觸發 `pull_request` `edited`；此時用的是含新 main 的 merge ref）、對該分支再 push（`synchronize`）、或在 PR 留一則留言（`issue_comment` 從 default branch／main 跑 workflow）。本單與接線都不要去改那些 PR、不要留言、不要 push 那些分支。

### O-020 Cloudflare 預覽留言會不會影響本檢查
依現行 `tooling/comment-lint.mjs`（本單不改）：只看留言正文開頭，不看作者、不讀 check run。會變紅的只有兩種：開頭是 `TechLead Review`（`CM-TECHLEAD`）；或開頭是 `QA`，且同一則留言有一行同時出現本機重跑用語（本機／重跑／box／worktree／locally／rerun／re-run）與指令（`pnpm check`、`pnpm db:test`、`pg_prove`、`supabase test db`）（`CM-QA-RERUN`）。沒有過濾 bot 作者。非 [G3] PR（含 `[G1]`／`[G2]`／`[D2]`，例如 #52～#54）在本單修正後仍不跑 comment-lint，只寫 not-checked success，因此 Cloudflare 在那些 PR 的留言或 check run **不會**讓本檢查變紅。預覽只限 `design/*` 時，`task/*` 的 `[G3]` PR 預期不會有 Pages 預覽留言。若 Cloudflare 出現在 `[G3]` PR，且正文開頭剛好命中上述規則，仍會變紅。不確定：官方文件沒有固定的留言作者登入名稱與正文開頭範本；分支控制略過建置時會不會仍留言，也未實測（見 `docs/tasks/O-020.md` 步驟 8）。

## 驗收標準
- AC-O21-1：標題不是 `[G3]` 開頭時，在 PR `head.sha` 寫入 `g3-comment-guard` success，description 恰好為 `not a [G3] PR; not checked`，exit 0；不讀留言、不跑 comment-lint。
- AC-O21-2：標題以 `[G3]` 開頭時，仍檢查三種留言並依 comment-lint 寫 success 或 failure；既有 [G3] 案例的 exit code 與 state 不得放寬。
- AC-O21-3：同一 head 先以非 [G3] 標題寫 not-checked success，再改成 `[G3]` 必須跑留言檢查並更新 status；反向則改回 not-checked success。不需改 workflow 觸發條件。
- AC-O21-4：讀不到標題或 head SHA、SHA 格式不符、或 status 寫入失敗時 exit 非 0，不得 silently success；SHA 未知時不寫 status；寫入目標不得是 merge SHA／`GITHUB_SHA`；新增或修改的檔案沒有未允許的 `|| true`、`continue-on-error`。
- AC-O21-5：測試沿用既有 `GH_BIN` 假 gh 模式，並比對 state、description 與 POST 路徑上的 SHA；覆蓋本單 TC；既有「非 [G3] 不寫 status」案例改為斷言會寫入 AC-O21-1 的 success，不得刪除這條覆蓋。
