## 背景（開始前先讀）
- `CLAUDE.md` §2、§3；`docs/RUNBOOK.md` §5（`ci-ok` 與 `Skipped (not verified)` 的意義）。
- 免費額度每月 2,000 分鐘，`ci.yml` 占大宗。GitHub 對每個 job 各自進位到整分鐘計費，`ci.yml` 每次 run 都有 5 個只跑數秒的小 job（`detect`、`actionlint`、`pushguard`、`secrets`、`ci-ok`），各算 1 分鐘。
- SRE 已決定 workflow 的新結構（見「SRE 接線」）：前 4 個小 job 合併成一個 `guard` job，`guard` 的第一步呼叫本單的 `tooling/ci-mode.mjs` 決定這次 run 的模式；`check`、`bundle`、`db`、`e2e`、`taskcheck` 依模式決定跑不跑；`ci-ok` 保留名稱與「彙總判定」語意。
- 三種模式：
  - `full`：照現在跑全部（PR、手動觸發、一般 push、任何判斷不了的情況）。
  - `docs`：推到 `main` 且只改文件；不跑 `check`、`bundle`、`e2e`（`db` 本來就只在 PR 跑）；`taskcheck` 只在有改 `docs/tasks/` 時跑（task-lint）。
  - `light`：推到 `task/**`、`fix/**` 且該分支已有開著、目標為 `main` 的 PR；重檢查以 PR run 為準。
- 不論哪一種模式，`guard` 裡的 actionlint、pushguard 測試、gitleaks 全歷史掃描、掃描器自測都照跑。
- 只用檔名判斷不夠：`tooling/news-source-seed.test.ts` 會 import `docs/ARCHITECTURE.md`、`tooling/gemini-a003-samples.test.ts` 會 import `docs/poc/A-003/samples/*`，所以「被程式引用的文件」要算程式。引用清單由 SRE 的接線用 `git grep` 算好，以檔案傳給本單的 CLI。

## 目標
以純函式機械地決定 ci run 的模式（`full`／`docs`／`light`），讓 SRE 的 workflow 據此少跑重 job。全部 fail-closed：任何輸入缺漏、格式不對或查詢失敗，一律 `full`。

## 介面
```ts
// tooling/ci-mode.mjs（只用 node: 內建模組）
export function isDocPath(path: unknown): boolean;
export function classifyChange(files: unknown, referenced: unknown): {
  docsOnly: boolean; tasksChanged: boolean; reason: string };
export function parseOpenPrs(body: unknown, branch: unknown): {
  prOpen: true | false | 'unknown'; prNumber: number | null };
export function decideMode(input: unknown): {
  mode: 'full' | 'docs' | 'light'; reason: string };
// input：{ event, ref, change: classifyChange 的結果或 'error', pr: parseOpenPrs 的結果或 'error' 或 'skip' }
export function run(argv: string[]): { code: number; stdout: string; stderr: string };
```
CLI：`node tooling/ci-mode.mjs decide --event <name> --ref <name> (--changed <path> --referenced <path> | --changed-error) (--pr <path> | --pr-error | --pr-skip)`。`--changed`、`--referenced` 是一行一個路徑的文字檔（可為空檔）；`--pr` 是 GitHub「列出 PR」API 的回應 JSON。stdout 為單行 JSON：`{"mode":…,"docs_only":<bool>,"tasks_changed":<bool>,"pr_open":true|false|"unknown"|null,"pr_number":<數字或 null>,"reason":<字串>}`。錯誤沿用其他 tooling CLI 的 `ci-mode: <RULE> …` 格式。

### 規則
- `isDocPath`：字串，且（以 `docs/` 開頭、但不以 `docs/poc/` 或 `docs/qa/` 開頭）或（不含 `/` 且以小寫 `.md` 結尾，例如 `README.md`）。空字串、以 `/` 開頭、含 `\`、含 `..` 路徑段、非字串 → false。巢狀的 `.md`（例如 `.claude/skills/run-task/SKILL.md`、`tooling/fixtures/tasks/O-901.md`、`apps/web/README.md`）→ false。
- `classifyChange`：`files` 必須是非空字串陣列、`referenced` 必須是字串陣列（可空）；否則 `docsOnly: false`。每個檔案都 `isDocPath` 且不在 `referenced` 裡 → `docsOnly: true`。`tasksChanged`：任一檔案以 `docs/tasks/` 開頭（不論 docsOnly）。`reason` 為固定代碼：`docs-only`、`code-path`、`referenced`、`empty`、`bad-input`。
- `parseOpenPrs`：`body` 必須是陣列、`branch` 必須是非空字串，否則 `unknown`。空陣列 → `false`。每個元素都必須是物件且 `state === "open"`、`head.ref === branch`、`base.ref === "main"`、`number` 是正整數；全部符合 → `true`，`prNumber` 取最小的 number；有任何一個元素不符 → `unknown`。`prOpen` 不是 `true` 時 `prNumber` 為 null。
- `decideMode`（依序判斷，第一個成立的為準）：
  1. `input` 不是物件，或 `event`、`ref` 不是非空字串 → `full`（`bad-input`）。
  2. `event` 不是 `push` → `full`（`event`）。`pull_request`、`workflow_dispatch` 一律 `full`。
  3. `ref === "main"`：`change` 是物件且 `docsOnly === true` → `docs`；其他（含 `'error'`）→ `full`。`pr` 不看。
  4. `ref` 以 `task/` 或 `fix/` 開頭：`pr` 是物件且 `prOpen === true` → `light`；其他（`false`、`unknown`、`'error'`、`'skip'`）→ `full`。`change` 不看（task 分支不用 docs 模式）。
  5. 其他 → `full`（`ref`）。
- 任何輸入都不得丟出例外。
- CLI：`--changed` 或 `--referenced` 讀不到 → 視同 `--changed-error`；`--pr` 讀不到或不是合法 JSON → 視同 `--pr-error`；以上都輸出 `full`、exit 0。`decide` 以外的子命令、無引數、`--event`／`--ref` 缺漏或重複、`--changed` 與 `--referenced` 只給一個、`--changed*` 或 `--pr*` 不是恰好一組 → `USAGE`，exit 1，stdout 不得有 JSON。輸出 JSON 的 `pr_open` 在 `--pr-skip` 時為 null。

## 限制
- 只用 Node 內建模組；不新增套件、不連網、不呼叫 `gh` 或 GitHub API（PR 回應一律用 fixture）。
- 不要執行 `pnpm db:test`、`supabase`、`psql` 或 `docker`。
- fixtures 一律是手寫的最小 JSON／文字（只放規則用到的欄位），不含任何 token 或帳號資料；不得放在 QA 擁有檔樣式的路徑。
- 測試寫成 `tooling/*.test.mjs`；CLI exit code 以 `child_process.spawnSync(process.execPath, …)` 實際斷言。
- 讀檔、搜尋一律用內建 Read／Grep／Glob 工具；不要用 Bash 的 `cat`、`grep`、`head`、`ls`、`sed`。
- 每一個 git 指令都是一次獨立的 Bash 呼叫，依序為：`git fetch origin`、`git switch -c task/O-015 origin/main`、`git add <明確檔案路徑…>`、`git commit -m "[Claude] O-015 …"`、`git push -u origin task/O-015`；每一次都不得含 `&&`、`;`、`|`、`2>&1` 或其他指令。

## SRE 接線（Claude Code 不做；不是 AC；Claude 的 run 成功、且 PR #42 合併後，由 SRE 在同一分支加 commit）
- `ci.yml`（`on:` 不加 `paths`／`paths-ignore`）：
  - 新 job `guard`（`fetch-depth: 0`；job 層 `permissions` 加 `pull-requests: read`）依序：①原 `detect` 的 has_* 旗標 ②模式：push 時以 `git diff --name-only "$BEFORE" "$SHA"` 取變更（BEFORE 為空、全 0 或 diff 失敗 → `--changed-error`），對每個文件路徑 `git grep -F -l` 查非文件檔有沒有引用（exit 1＝沒有、其他非 0 → `--changed-error`）；push 到 `task/**`、`fix/**` 時以 `gh api "repos/<repo>/pulls?state=open&base=main&head=<owner>:<branch>"` 查 PR（失敗 → `--pr-error`），其他 → `--pr-skip`；呼叫 `ci-mode.mjs decide`，exit 非 0 → job 失敗 ③actionlint ④pushguard 原有的全部測試 ⑤gitleaks 全歷史＋`secret-selftest.mjs`。③～⑤ 沒有 `if:`，三種模式都跑。outputs：has_*、`is_pr`、`mode`、`tasks_changed`、`pr_number`。
  - `check`、`bundle`、`e2e`、`db`：`needs: guard`，原條件再加 `mode == 'full'`。`taskcheck`：（`mode == 'full'` 且原條件）或（`mode == 'docs'` 且 `tasks_changed == 'true'`）。
  - `ci-ok`：名稱不變，`needs: [guard, check, bundle, db, e2e, taskcheck]`、`if: always()`，以 env 傳入 `MODE`、`PR_NUMBER`。
- `ci-ok.mjs`：`REQUIRED = ['guard']`（skipped 也算失敗）；`MODE` 不是 full／docs／light → 失敗；`pull_request` 事件而 MODE 不是 full → 失敗；任何 job failure／cancelled → 失敗（不分模式）。摘要照舊列 `Skipped (not verified)`，另加一行模式說明：docs ＝「只改文件：check、bundle、e2e 依路徑略過（未驗證）」，light ＝「PR #<n> 的 pull_request run 為準」。push run 略過 PR 才跑的 job 仍不算綠燈（沿用 C4 說明）。
- 接線測試（box 上與 `guard` job 都跑；突變後測試必須失敗）：
  - W-1 純文件推 main：`guard` 的 actionlint、pushguard、gitleaks 步驟都執行；`check` 略過；改了 `docs/tasks/` 時 `taskcheck` 執行。
  - W-2 文件＋程式混合推 main，或只改被程式引用的 `docs/ARCHITECTURE.md` → `full`，`check` 執行。
  - W-3 PR 查詢失敗（以 stub 的 `gh` 回非 0 或壞 JSON）→ `full`；diff 失敗、BEFORE 全 0 → `full`。
  - W-4 `ci-ok.test.mjs`：`guard` failure／skipped／缺漏 → 失敗；docs 模式下 `taskcheck` failure → 失敗；PR 事件＋docs 或 light → 失敗；MODE 缺漏 → 失敗。
  - W-5 workflow 靜態檢查（`.github/scripts/ci-workflow-check.mjs`＋測試）：`on:` 沒有 `paths`／`paths-ignore`；`guard` 的 ③～⑤ 沒有 `if:`；重 job 的 `if` 含 `mode`；`ci-ok` 的 `needs` 含全部 6 個 job；`fail-open-lint` 通過。
  - 突變：拿掉 REQUIRED 的 `guard`、刪掉 PR 事件的 full 檢查、把 `--pr-error` 改成 light、給 gitleaks 步驟加 `if: mode == 'full'`、在 `on:` 加 `paths-ignore`，W-4／W-5 必須失敗。
  - 實測（push run 與 PR run 各一，貼 run 連結）：task/O-015 開 PR 前的 push → full；開 PR 後的 push → push run light、PR run full 且 `ci-ok` 綠；合併後第一次純文件推 main → docs（由下一次推任務單的 SRE 確認）。
- `docs/RUNBOOK.md` §5：三種模式、`guard` 取代 4 個小 job、`light` 時以 PR run 為準。
- 為什麼不用 workflow 層的 `paths-ignore`：整個 workflow 不會觸發，`ci-ok` 這個 check 根本不出現；之後設成必要檢查時，只改文件的 PR 會一直停在「等待中」不能合併；同時 gitleaks 與 pushguard 也不會跑，文件裡的密鑰就沒人擋。所以改在 `guard` 裡判斷，`ci-ok` 每次都會出現並給出結果。
