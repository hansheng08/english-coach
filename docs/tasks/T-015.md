## 目標
依 ARCHITECTURE §5.4 實作免費 `gemini` 的 LLM adapter（`generate`／`stream`，只用注入的 `fetch` 呼叫 REST）與 `loadGeminiKey`，以 A-003 實測樣本回放做契約測試，並把 ADR-008 修訂 5 第 18、19 條加進 dependency-cruiser（PRD AC-24、AC-25、NFR-05）。付費 adapter 的建立（registry 的 `paidFactories`、`wiring.ts`）不在本單。

```ts
export type GeminiDeps = { readonly id: 'gemini' | 'gemini-paid'; readonly apiKey: string; readonly fetch: typeof fetch };
```

§5.4.4 要求「錯誤分類寫成一個純函式」，名稱與檔案是 TechLead 決定：
```ts
// supabase/functions/_shared/providers/gemini/errors.ts（只給同資料夾與測試用）
export function classifyGeminiError(input: { readonly status: number; readonly body: string; readonly id: 'gemini' | 'gemini-paid'; readonly model: LlmModelId; readonly apiKey: string }): ProviderError;
```

## 驗收標準
- **AC-T15-1**（NFR-05；§5.4.2）`loadGeminiKey` 只讀 `GEMINI_API_KEY`：`undefined`、空字串、只有空白 → `not_configured`（`provider: 'gemini'`、`capability: 'llm'`、`message: 'missing env GEMINI_API_KEY'`）；有值原樣回傳。`loadGeminiPaidKey` 也把只有空白當成沒有，其餘行為不變。
- **AC-T15-2**（AC-24；§5.4.2）`createGeminiProvider` 依 `id` 決定 `tier`（`gemini-paid` → `paid`，其餘 `free`）與 `displayName`（`Gemini`／`Gemini（付費）`），`capability` 是 `llm`；建立時不呼叫 `fetch`。
- **AC-T15-3**（§5.4.3）請求：`POST` 到 §5.4.3 的端點（`{model}` 直接放 `LlmModelId`；串流用 `:streamGenerateContent?alt=sse`），金鑰只在 `x-goog-api-key` 標頭、不在網址；內容只有 `systemInstruction`、`contents`、`generationConfig.maxOutputTokens`，`generate` 另加 `responseMimeType: 'application/json'`；不送 `thinkingConfig`、`temperature`、`topP`、`topK`、`responseJsonSchema`。
- **AC-T15-4**（AC-24；§5.4.3）`generate` 成功：取 `candidates[0].content.parts` 中 `thought !== true` 且非空的 `text` 依序串起，`JSON.parse` 後用 `req.schema.safeParse`，回傳驗證後的值；回應 schema 不用 strict，A-003 的 `thoughtSignature` 等多出欄位不影響。
- **AC-T15-5**（AC-25、ADR-003；§5.4.4）自動重試只有一種：`finishReason` 為 `STOP` 但 `JSON.parse` 或 zod 失敗 → 同模型再呼叫 1 次，第 2 次仍失敗回 `invalid_response`；其他任何錯誤都只呼叫 1 次；每次 `generate` 最多呼叫 `fetch` 2 次。
- **AC-T15-6**（AC-25；§5.4.4）`classifyGeminiError` 依 §5.4.4 表由上往下比對、取第一列符合的；已實測的列用 A-003 樣本（`05`、`05b`、`06`、`07`、`07b`、`02-gen-gemini-3.8-flash`）測，未驗證的列（429 兩列、402、`region_blocked`、401、408／504、500／502、其他狀態碼）用依文件做的樣本測；錯誤內容不是 JSON 時只依 HTTP 狀態判斷。2xx 但內容不是 JSON 或結構不符 → `invalid_response`。
- **AC-T15-7**（§5.4.5）`finishReason` 對應：`generate` 與 `stream` 都照 §5.4.5 表的每一列（含 `CONTINUATION`、`LANGUAGE`、`ESCALATION`、`PUP_LIMITED_DISABLED`、未知新值）；`generate` 的 `promptFeedback.blockReason` → `invalid_response`（訊息含 `blocked: <原因>`）。
- **AC-T15-8**（AC-24；§5.4.6）`stream`：CRLF 切段、只讀 `data:` 行、每段非空文字產生一個 `delta`、最後一段只產生 `done`（`usage` 取最後一段，不相加）；非 2xx 依 HTTP 狀態當一般 JSON 解析、產生一個 `err`；途中 `{ error }` 段、壞段、沒有 `finishReason`、`blockReason` 都照 §5.4.6；產生 `err` 後不再產生任何東西；串流不重試。
- **AC-T15-9**（§5.4.3、§6 第 6 點）逾時是必要條件：`generate` 與 `stream` 都在 `timeoutMs`（整段時間）自己中止，回 `timeout`，且傳給 `fetch` 的 `signal` 已被中止；`fetch` 丟出網路錯誤或串流中途讀取失敗 → `unavailable`；呼叫端提前停止讀取串流 → 中止底層請求、不再產生東西。
- **AC-T15-10**（NFR-05；§5.4.2）金鑰保護：任何 `ProviderError.message` 都不含金鑰字串，出現時換成 `[redacted]`（錯誤內容回顯金鑰、`fetch` 例外訊息含金鑰兩種情況都要測）。
- **AC-T15-11**（ADR-008 修訂 5）dependency-cruiser 有第 18 條（adapter 子資料夾的正式程式只能 import `contracts`、`zod`、同資料夾）與第 19 條（只有 `providers/wiring.ts` 與測試可 import `config/provider-keys.ts`），用 ADR-008 修訂 5 的 4 個範例做 fixture 測試；真實程式樹 `pnpm arch` 0 違規。
- **AC-T15-12**（CLAUDE.md §7；§5.4）測試不連網：所有測試只用注入的假 `fetch`，全域 `fetch` 被替換成一呼叫就失敗的函式，且呼叫次數為 0；A-003 樣本防漂移檢查通過。

- adapter 正式程式不 `throw`，一律回 `Result`；`stream` 用 `Result<StreamChunk, ProviderError>` 表達錯誤（§6 第 1 點）。不用 `as unknown as`。相對 import 寫 `.ts` 副檔名。
- 不送 `thinkingConfig`、不做指數退避、不在 adapter 內換模型或換供應商（ADR-012 決定 1、4）。
- 本單不涵蓋（未驗證，見 ADR-012「驗證」表）：真實 429 的 `details` 格式、`region_blocked` 訊息、`gemini-3.8-flash` 的成功回應、串流途中出錯的真實格式。這些列照 §5.4 實作並以依文件做的樣本測試；真實格式不同時另開修正單。

## 驗證方式
`pnpm check` 跑到通過；任務單不另列指令。

## 結束時
1. 在指定的分支上 commit 並 push，不得動 main。
2. 把結果寫到 docs/reports/T-015.md：完成摘要、變更檔案、測試結果、未完成事項、需要人類決定的問題。
3. 測試結果、突變結果、權限被拒以 workflow 自動產生的摘要與 PR 觸發的 CI run 為準，報告不重貼。
