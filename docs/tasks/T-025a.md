## 目標
每天台北 05:00 由 `daily-prep` 為每位使用者備好當天計畫；App 開啟時 `POST /plan/today` 冪等補做或直接回傳。兩者共用 `preparePlan`，用 `claimed_at` 租約保證同一天只有一個備料者。

## 介面
§4.13、§4.14.4 已定的名稱與簽章照 ARCHITECTURE；以下是 TechLead 補的決定：
```ts
// packages/contracts/src/plan.ts：照 §4.13.1、§4.14.1 全部（NoonMaterialResponseSchema 屬 T-025b，不做）
// packages/domain/src/noon.ts（本單：selectNoonMode、recallPrompt 照 §4.14.4 全部規則）
export type NoonCardInput = NoonCardFields & { readonly cardId: CardId; readonly chunk: string };
export function buildNoonItem(card: NoonCardInput, llmItem: undefined, planDate: PlanDate): NoonItem;
// supabase/functions/_shared/plan/prepare.ts
export type PlanDeps = { readonly store: PlanStore; readonly llm: Result<RewriteDeps, ProviderError>;
  readonly fetch: FetchLike; readonly now: () => Date; readonly log: (e: NewsEvent) => void };
export type ClaimResult = { readonly kind: 'claimed'; readonly claimedAt: string } | { readonly kind: 'existing'; readonly plan: DailyPlan };
export const CLAIM_LEASE_SECONDS = 180;
```
- `buildNoonItem` 本單只接受 `undefined`（T-025b 放寬成 LLM 素材）：回 `card_id`，`cloze_en` 照 §4.14.2（例句 `detectChunkHits` 為 `full` 時把 `matchedText` 第一次出現處換成 `____`），其他欄位 null。
- `ClaimResult.claimed` 多帶 `claimedAt`：§4.13.2「完成」條件要用自己搶到時的值。租約判斷用 `deps.now()` 減 180 秒的 ISO 字串當條件，重新認領時 `claimed_at` 也寫 `deps.now()` 的值。
- **`PlanStore`**（`supabase/functions/_shared/db/plan-store.ts` 的 `planStoreFrom(client, userId)`；全部回 `Promise<Result<…, AppError>>`，每個查詢都帶 `user_id = userId`，所以使用者 client 與 secret client 共用同一個實作，CLAUDE.md §5 第 15 條）：
  `insertPending`、`readPlan`（含組 `DailyPlan` 需要的文章、來源名稱、題目；`failed` 時讀 `failure` 欄）、`reclaim`、`complete`／`fail`（`fail` 收一個 `PlanFailure`，同一個 update 寫 `status = 'failed'`、`error = failure.error.kind`、`failure`；條件 `status = 'pending' and claimed_at = <claimedAt>`，回 `boolean`）、`readNewsSettings`（`settings.news` 缺少時用 `NewsSettingsSchema.parse({})`；不合法 → `internal`）、`listNewsSources`、`isArticleUsed`、`insertArticle`、`readFallbackArticle(planned)`（`read_at is null`，`planned` 類別優先，再依 `published_at` 新到舊）、`listCardCandidates`、`listQuestionCandidates`（`timesAsked`、`lastAskedDate` 由 `kind = 'first'` 的回答算，日期換台北）。
- **`preparePlan` 順序**（搶到認領後）：
  1. `planned = plannedCategory(planDate, settings)`；依 `categoryTryOrder` 每類呼叫 `findArticle`：`news_unavailable` → 記入 `skipped` 換下一類；其他 `err`（判定或改寫失敗、`deps.llm` 是 `err`）→ 直接走第 3 步（§11.3.5、ADR-013 決定 6）。
  2. 找到 → `rewriteArticle`；成功就 `insertArticle`（§11.3.1 第 4 步的欄位），`actual` 是該類；改寫失敗 → 第 3 步。
  3. 舊文章：`readFallbackArticle(planned)`；有 → `is_fallback_article = true`、`actual` 是該文章的類別、`skipped` 是三類全部；沒有 → 照下面的「失敗原因」寫 `fail`。
  4. 跟讀：`selectShadowSentences(新聞句, null)`；`containsTargetChunk` 是該句含文章 5 個語塊之一（`chunkAppearsIn`）；`tts_path` 一律 null。改寫句參數固定 null（見「不在本單」）。
  5. 選卡與中午：照 §4.14.5 第 1～6 步，`seeds` 空陣列、`usedSeedChunkIds` 空集合、`llmItem` 一律 `undefined`；`card_ids` 依 `selectDailyCards` 的舊卡、新卡、補位舊卡順序。
  6. 今晚題目：`selectTonightQuestion`；回 null（題庫還是空的）時 `tonight_question_id` 為 null（#91 合併時核准的過渡做法）。
  7. `complete` 一次寫入全部欄位與 `status = 'ready'`；回 `false`（被接手）時丟掉結果、改回 `readPlan` 的內容。任何一步回 `err` → 照「失敗原因」寫 `fail`。
- **失敗原因**（§5.9.2；`step` 的對應由 TechLead 定）：`failure` 是 `{ step, error: toApiErrorBody(e).error, timeout_sec, failed_at }`，`failed_at` 是 `deps.now()` 的 ISO 字串（帶時區）。`step`：三類都 `news_unavailable`、又沒有舊文章 → `news`（`error.kind` 是 `news_unavailable`）；判定、改寫或 `deps.llm` 的錯誤讓本單改找舊文章、又沒有舊文章 → `rewrite`（`error` 是那個 LLM 錯誤）；第 1～3 步其他錯誤（例如 `db_failed`）→ `news`；第 5 步 → `cards`；`complete` 本身的錯誤 → `save`；其他 → `internal`。`timeout_sec`：`error.kind` 是 `timeout` 時填那次呼叫的 `timeoutMs` ÷ 1000（判定 8、改寫 30；`rewrite.ts` 把這兩個值匯出成 `JUDGE_TIMEOUT_MS`、`REWRITE_TIMEOUT_MS`，數值不改），否則 null。
- **`rewrite.ts` 修正**（TASKS 原 T-025 列，PR #41 QA 發現）：`excerpt` 改成**先正規化，再移除標記**：先用 `newsWords` 切字接回，再移除 `<<<ARTICLE>>>`、`<<<END ARTICLE>>>`，移除後再正規化，重複到不含任何標記，最後取前 `n` 個字。
- **`RouteDeps`** 加三個**選填**欄位：`planStore?: (ctx: AuthContext) => PlanStore`、`providers?: Registry`、`fetch?: FetchLike`；`UserDb`、`DbClient` 不改。理由同 T-032 v1.1：T-053 的 QA 探針（`checkins.qa.test.ts`、`checkins-path.qa.test.ts`）直接寫出 `RouteDeps`、`UserDb`，加必填欄位會讓它們編譯失敗。`postPlanToday` 開頭檢查三欄，任一缺少 → 500 `internal`、不呼叫任何依賴。`index.ts` 三欄都接：`planStore` 用 `planStoreFrom`（使用者 client 的建法和既有的 `userDb` 相同），`providers` 用 `createProviders({ env: denoEnv, fetch })`。`POST /plan/today`（`api/plan.ts` 的 `postPlanToday`）不收 body；`llm` 用 `providers.resolve('llm', DEFAULT_SETTINGS, 0)`（ADR-012 決定 6；免費供應商不看用量），`model` 是 `DEFAULT_SETTINGS.llm.model`；成功 → 200＋`DailyPlan`（`failed` 也是 200，body 帶 `failure`，§5.9.1）。
- **`wiring.ts`**：`createProviders(deps: { env: EnvGetter; fetch: typeof fetch }): Registry`；`loadGeminiKey` 成功才放入 Gemini adapter，失敗時清單是空的（`resolve` 自然回 `not_configured`）。
- **`daily-prep`**（`daily-prep/handler.ts` 的 `createDailyPrepHandler`，`index.ts` 只做組裝，同 T-046 寫法）：`env` 錯 → 500；`requireServiceKey` 不過 → 401；之後 `service-db.ts` 新增的 `listProfileUserIds` 逐一 `preparePlan`（`planDate` 是 `toTaipeiPlanDate(now)`），回 200＋`{ ready, existing, failed }` 筆數；log 只有筆數與錯誤 `kind`。
- **migration**（`supabase/migrations/<時間戳記>_t025a_daily_plan_claim_noon.sql`；時間戳記規則同 T-046）：`claimed_at`、`noon_items`、`failure jsonb` 與它們的 check（§4.13.2；`failure` 的 check 是 `(status = 'failed') = (failure is not null)`，§4.13.1）；`error` 的 check 列出 `APP_ERROR_KINDS` 全部值（§4.13.1）；兩個 `create extension if not exists`；`cron.schedule('daily-prep-daily', '0 21 * * *', …)`，呼叫寫法照 §4.12.3、路徑 `/functions/v1/daily-prep`、`timeout_milliseconds := 150000`。
- **`config.toml`**：加 `[functions.daily-prep]` 兩行（CLAUDE.md §5 第 16 條）。
