## 目標
使用者在設定頁改複習間隔、模型與供應商、「不評分」、朗讀聲音、預取開關與付費同意，存檔後下一次請求就用新設定；設定頁顯示本月付費用量（估算）。伺服器用同一套 schema 驗證，不合格時標出哪一格、什麼都不寫。

## 介面
§4.15.1 的 `ProviderSettingsSchema`、`SettingsSchema`（`monthly_paid_cap_ntd` 用 `MonthlyPaidCapNtdSchema`，同意時不可為 null 的 refine），§4.15.2 的 `SettingsPatchSchema`、合併規則 1～7、`SettingsResponseSchema`，§4.15.3 的 `SlotStartSchema`（只建 schema；時段 UI 是 T-047），§4.15.5 的上限規則（0～1000 或 null、預填 300），§4.15.6 的欄位、估算規則（`USD_TO_NTD = 35`，contracts `src/billing.ts`）與 `sumPaidUsageThisMonthNtd` 照 ARCHITECTURE；以下是 TechLead 補的決定：
```ts
// supabase/functions/_shared/db/settings-store.ts（新增；照 user-db.ts）
export type SettingsStore = {
  readonly read: () => Promise<Result<{ readonly settings: unknown; readonly slotStart: unknown }, AppError>>;
  readonly write: (settings: Settings, slotStart: SlotStart | null) => Promise<Result<null, AppError>>;   // 付費鍵保留原值
  readonly setPaidConsent: (consent: boolean, capNtd: Ntd | null) => Promise<Result<null, AppError>>;  // 轉呼叫 paid-consent.ts
  readonly paidUsageThisMonthNtd: (now: Date) => Promise<Result<Ntd, AppError>>;
};
// supabase/functions/api/settings.ts（新增）；RouteKey 加 'GET /settings'、'POST /settings'
export const getSettings: Route;
export const postSettings: Route;
// apps/web/src/api/client.ts：ApiClient 加
//   getSettings(): Promise<Result<SettingsResponse, AppError>>;  saveSettings(p: SettingsPatch): 同上
```
- **`postSettings` 順序**：body 照 §5.1.1 用 `SettingsPatchSchema` → `read` → `SettingsSchema.parse`（不合格 → 500 `internal`，不換預設）→ `mergeSettings` → 合併後整份 `SettingsSchema`（不合格 → 400 `validation`、`issues` 帶路徑如 `srs.step_days.1`）→ 有 `paid` 先 `setPaidConsent` → `write` → 回 `SettingsResponseSchema`。任何一步失敗都不寫後面的步驟；`paid` 成功、`write` 失敗時回 500，報告寫明這個順序。
- **付費鍵**：`write` 送出的 jsonb 不含 `paid_consent_at`、`monthly_paid_cap_ntd`，用 `settings || <新值>` 的寫法讓兩個鍵維持原值（§4.15.2 第 7 點）；pgTAP 測寫回後兩個鍵不變。
- **`_shared/db/paid-consent.ts`**（§4.9 第 1 點指定的呼叫端，新增）：`setPaidConsent(serviceClient, userId, consent, capNtd)` 以 `ctx` 的 `user_id` 呼叫 `set_paid_consent()`；它是 `api` 裡唯一用 secret 金鑰的程式，只有 `supabase/functions/api/**` 可以 import（ADR-008 修訂 4，第 17 條）。`SettingsStore.setPaidConsent` 只轉呼叫它。
- **`registry.ts`**：`ProviderSettings` 改成 import contracts 的型別；`DEFAULT_SETTINGS` 改成 `SettingsSchema.parse({})` 的那幾組；`PROVIDER_TIERS` 搬到 contracts（§5.9.4），`registry.ts` 重新匯出，行為不變。
- **用量接線**（§4.15.6、ADR-019 決定 4）：main 上已有的每個 `registry.resolve` 呼叫點（T-025a 的 `daily-prep` 與 `/plan/today`、T-021 的 `/tts`，以及本單合併時已在 main 的其他呼叫點）都改成傳 `sumPaidUsageThisMonthNtd(…)`；T-021 等單在本單合併前依 §4.19 暫時傳的字面 `0` 在這裡全部換掉，換完不得留任何字面 `0`；報告列出改了哪幾處。
- **`provider_call`**：migration 加三欄（照 §4.15.6，`grant insert` 清單與 `PROVIDER_CALL_COLUMNS` 同步）；`ProviderCallRecord` 加 `inputTokens`、`outputTokens`（`number | null`），`providerCallRow` 用 `_shared/billing/estimate.ts` 的 `estimateCostNtd(record)` 算 `cost_ntd`（`tier = 'free'` 是 0；付費有 usage 照 contracts 單價表與 `USD_TO_NTD = 35` 無條件進位；付費沒有 usage 是 1；請求沒送出不寫列或 `cost_ntd = 0`）。
- **前端**：
  - 路由 `/settings`（`RequireSession`）；頭像選單（`AccountMenu`）加「設定」連結（`screens/settings.md` §1 的入口之一；底部分頁與頂部導覽不在本單，見「不在本單」）。
  - 區塊：外觀（重用既有主題切換）→ 複習間隔 → 模型與供應商 → 付費 → 履歷 → 帳號。**不放**「新聞輪替」（`settings.md` §4 PM 決定）；「時段開始時間」由 T-047 加在外觀之後。
  - 履歷列只放連到 `/resume` 的連結「履歷與面試題」；檔名與題數由 T-036 補（T-036 合併前沒有資料來源）。
  - `apps/web/src/ui/provider-labels.ts`（§5.9.4 的表與朗讀語音顯示名稱 `Record<VoiceId, string>`，窮舉：Ava（女聲）、Andrew（男聲）、Kore（女聲）、Puck（男聲））與 `ui/ProviderMeta.tsx`（把 `meta` 的 ID 轉成「Gemini・Gemini 3.5 Flash-Lite」，付費加「（付費）」看供應商不看模型）。

- **AC-T20-6**（§4.15.6、ADR-019 決定 4）`provider_call` 三欄與 `grant insert` 清單、`PROVIDER_CALL_COLUMNS` 一致；`estimateCostNtd` 照三種情況，匯率用 `USD_TO_NTD = 35`；`sumPaidUsageThisMonthNtd` 只加總台北日曆月內 `tier = 'paid'` 的列，沒有列回 0；main 上每個 `resolve` 呼叫點都傳這個值，§4.19 的過渡 `0` 已全部換掉（`rg` 找不到 `resolve(` 後面傳字面 `0`）。
