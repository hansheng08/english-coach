## 背景
- 開始前先讀：`CLAUDE.md`；RUNBOOK §6.3（ci-guard 與 full／docs／light）、§6.4（CI 成本 lint）；`tooling/ci-mode.mjs` 與其測試；`.github/scripts/ci-guard-mode.sh`、`.github/scripts/ci-ok.mjs`（只讀，SRE 改）。
- 現況：`ci-guard` 的「Decide CI mode」步驟由 `ci-guard-mode.sh` 準備輸入、`tooling/ci-mode.mjs decide` 決定模式。推到 `task/**`、`fix/**` 時，只有「已有開著、目標 main 的 PR」才降 `light`；還沒開 PR 一律 `full`（`check`、`taskcheck` 等全跑）。`ci-ok.mjs` 的 light 一定要有 PR 編號。
- QA 在 G3 PR 開之前常分幾次推補充測試（`*.qa.test.ts`、`docs/qa/mutants/*.json`），每次都跑一輪完整 push CI，但 G3 PR 開了之後 pull_request run 一定會再跑完整的一次。
- 2026-11-27：#82 的 push run 45915119472 紅燈，原因是分支上還是 #81 合併前的舊 `taskcheck`（假紅燈）。之後為了消紅燈把 main merge 進分支，又多跑一輪完整 CI。當時同一個 head 的 PR run 才是必過檢查的依據，push 紅燈本來可以不管。
- 必過檢查只有 `ci-ok`（只有 pull_request run 產生這個名稱）與 `g3-comment-guard`；push run 的彙總名稱是 `ci-ok (push)`，綠了也不算。本單不改這一點。

## 目標
1. 推到 `task/**`、還沒開 PR、且這次推送只改「QA 檔」時，降成 `light`（只跑 `ci-guard` 的安全掃描）。
2. 還沒開 PR 時，同一分支連續兩次推送都只改 QA 檔，發一則 `::warning`（只警告，不擋）。
3. 同一個 head SHA 上，PR run 的 `ci-ok` 綠、push run 紅時，打一個非必過的 commit status 註記「push 紅燈已被 PR 結果取代」。

## 定義（本節凍結）

### QA 檔（第 1、2 項共用）
路徑一律是 repo 根目錄的相對路徑，以 `git diff --no-renames --name-only` 的輸出逐行判斷；新增、修改、刪除都一樣判斷路徑。**全部**符合下列其中一條才算 QA 檔：

| 規則 | 路徑樣式 | 依據 |
|---|---|---|
| Q1 單元／QA 測試 | `apps/**`、`packages/**`、`supabase/**` 底下，檔名以 `.test.ts`、`.test.tsx` 結尾（含 `*.qa.test.ts`） | `vitest.config.ts` 的 include |
| Q2 pgTAP 測試 | `supabase/tests/*_test.sql`（只一層） | `pnpm db:test` 讀的目錄 |
| Q3 E2E 規格 | `test/e2e/**/*.spec.ts` | `playwright.config.ts` 的 `testDir`＋`testMatch` |
| Q4 QA 文件 | `docs/qa/**` | 憲章 §5 QA 擁有檔（mutants.json） |

明確**不算** QA 檔（出現任何一個就 `full`）：
- 測試目錄裡的非測試檔：`apps/web/test/setup.ts`、`*.d.ts`、`packages/contracts/test/index.ts`（以 `./testing` 匯出給其他套件）、`supabase/functions/**/test/*.ts` 的 fake／fixture、`test/e2e/tsconfig.json`。它們會被多個測試或其他套件引用，影響範圍不只單一測試。
- `tooling/**`（含 `tooling/*.test.mjs`、O 單的 vitest 包裝）、`.github/**`（含 `.github/scripts/*test*`）、`.claude/**`：這些是 CI 自己的檢查工具，改了就要跑完整 CI 證明檢查本身沒壞。
- 設定與依賴：`vitest.config.ts`、`playwright.config.ts`、`package.json`、`pnpm-lock.yaml`、`tsconfig*.json`、`eslint.config.js`、`.dependency-cruiser.cjs` 等。
- 快照與基準圖（`__snapshots__/**`、`*.snap`、截圖基準）：憲章 §15.9 把更新基準圖視為設計變更，要完整 CI。
- 絕對路徑、含 `..`、含反斜線、空字串。

### 「前一次推送」（第 2 項）
用 GitHub repository activity API（`GET repos/<repo>/activity`，`ref=refs/heads/<分支>`、`activity_type=push`，只讀第一頁）找出 `after` 等於這次 `BEFORE_SHA` 的那筆紀錄，它的 `before..after` 就是前一次推送的範圍。下列任一情況「無法判定」，**不發警告**（只警告的功能，判不出來就不警告，可接受）：API 失敗或回應格式不對、找不到符合的紀錄、`before` 不是 40 位 hex 或全 0、`before` 不在 clone 裡或不是 `after` 的祖先、diff 失敗。

### 取代註記（第 3 項）
commit status，context 固定為 `ci-push-superseded`（不以 `ci-ok` 開頭，避免和必過檢查混淆；**不得**加進分支保護）。「取代」成立的條件，全部成立才算：
1. `ci.yml` 在這個 head SHA 上，最新一個 `pull_request` run（依 run id 取最大）是同 repo 的 PR（`head_repository.full_name` 等於本 repo，非 fork）、已完成，且其中名稱**恰好**是 `ci-ok` 的 job 為 `success`；`pull_requests` 有一個正整數 PR 編號。
2. 同一個 SHA 上最新一個 `push` run（依 run id 取最大）的分支是 `task/**` 或 `fix/**`、已完成、`conclusion` 為 `failure`。
不採用 PR 留言：G3 PR 上的每則留言都會被 `g3-comment-guard` 檢查，自動留言會增加誤判與雜訊；commit status 同 context 後寫覆蓋前寫，天生不重複。

## 介面

### `tooling/ci-mode.mjs`（Claude 改；既有 main 的 docs 判斷與 PR 判斷行為不變）
```text
export function isQaPath(path)            // 依「QA 檔」Q1～Q4；其餘一律 false
export function classifyQa(files)         // { qaOnly: boolean, reason: string }；空清單 qaOnly=false
export function decideMode(input)         // input 新增 qa: classifyQa 結果 或 'error'
CLI decide 新增（只在 --ref 為 task/**、fix/** 時接受，其他 ref 傳了就 USAGE）：
  --qa-changed <file> | --qa-changed-error          （task/**、fix/** 時必須恰好給一個）
  --prev-qa-changed <file> | --prev-skip            （task/**、fix/** 時必須恰好給一個）
輸出 JSON 新增欄位：qa_only (boolean)、qa_batch_warning (boolean)
```
決策（依序，fail-closed）：
- 推到 `task/**`／`fix/**` 且有開著的 PR → `light`／`branch-with-open-pr`（不變）。
- 推到 `task/**`、PR 查詢結果明確為「沒有 PR」、`qa.qaOnly === true` → `light`／`tests-only-no-pr`。
- 其餘（`fix/**`、PR 查詢失敗、`--qa-changed-error`、檔案讀不到、清單空、有任何非 QA 檔）→ `full`。
- `qa_batch_warning` 只在 reason 為 `tests-only-no-pr` 且前一次推送的清單 `classifyQa` 也是 `qaOnly` 時為 `true`；`--prev-skip` 或讀檔失敗一律 `false`。它不得改變 `mode` 或 exit code。

### `tooling/ci-supersede.mjs`（Claude 新增）
```text
export function decideSupersede({ sha, repo, runs, jobs, existing })
  // runs: ci.yml 在此 sha 的 workflow runs（API 原樣陣列）
  // jobs: { [runId]: jobs 陣列 }；existing: 此 sha 上 context=ci-push-superseded 的 statuses（新到舊）
  // 回傳 { action: 'mark' | 'retract' | 'none', reason, prNumber, prRunId, pushRunId, description }
CLI: ci-supersede.mjs decide --sha <sha> --repo <owner/name> --runs <file> --jobs <file> --existing <file>
```
- `mark`：「取代」條件成立，且 `existing` 最新一筆不是同一個 `prRunId` 的 `success`。`description` ≤ 140 字元，含 push run id 與 PR 編號，並寫明「非必過、請勿為消紅燈重推」。
- `retract`：條件不成立，但 `existing` 最新一筆是 `success`（例如 PR run 重跑後變紅）。
- `none`：其他情況（含已標過同一 PR run）。
- 輸入檔缺、非 JSON、欄位型別不對、`sha` 不是 40 位 hex → `INPUT`／非 0，不得印出 `mark`。

## 驗收標準
- AC-O28-1：`isQaPath` 對 Q1～Q4 為 true；對「不算 QA 檔」列出的每一類（至少各一例）為 false。
- AC-O28-2：推到 `task/**`、明確沒有 PR、清單全是 QA 檔 → `light`／`tests-only-no-pr`；同樣輸入但 ref 是 `fix/**`、`main`，或事件是 `pull_request` → 不得是這個 reason（PR run 一律 `full`）。
- AC-O28-3：fail-closed：`--qa-changed-error`、清單空、混一個非 QA 檔、PR 查詢失敗或回應不明 → `full`。
- AC-O28-4：`qa_batch_warning` 只在「這次 `tests-only-no-pr`＋前一次也只改 QA 檔」為 true；`--prev-skip`、前一次有非 QA 檔、這次已有 PR 或是 `full` → false；兩種值的 `mode` 與 exit code 相同。
- AC-O28-5：`decideSupersede` 在「取代」條件成立時回 `mark`，並帶正確的 PR 編號與兩個 run id。
- AC-O28-6：下列任一 → 不得 `mark`：PR run 的 `ci-ok` 不是 success 或找不到恰名 `ci-ok` 的 job（`ci-ok (push)` 不算）；最新 PR run 紅但較舊的 PR run 綠；push run 是 success 或未完成；PR 來自 fork；沒有 PR run；run 的 `head_sha` 和 `--sha` 不同。
- AC-O28-7：已標過同一 PR run → `none`；條件不再成立且先前是 success → `retract`；輸入不合法 → `INPUT`／非 0。
- AC-O28-8（SRE 接線）：`ci-ok.mjs` 只在 `task/**` push、reason 為 `tests-only-no-pr`、PR 編號為空時接受沒有 PR 編號的 light；其他沒有 PR 編號的 light、或 reason 與 PR 編號不一致，一律失敗。摘要寫明「本 push run 綠燈不算數，以之後 G3 PR 的 pull_request run 為準」。
- AC-O28-9（SRE 接線）：取代註記 workflow 只用 `workflow_run`；權限只有 `contents: read`、`actions: read`、`statuses: write`；checkout 預設分支（不帶 `ref`、不 checkout PR 的 head）且 `persist-credentials: false`；不用任何 secret；fork 的 run 不處理；分支保護的必過檢查不變。
- AC-O28-10：突變必須被抓到：把 `tooling/**` 或設定檔當 QA 檔；`fix/**` 也降 light；PR 查詢失敗仍降 light；`qa_batch_warning` 讓 exit code 變非 0；把 `ci-ok (push)` 當成 PR 的 `ci-ok`；接受 fork PR run；不比對 `head_sha`。上述削弱若仍能通過測試，本 AC 失敗。
- AC-O28-11：本單新增或修改的檔案沒有未允許的 `|| true`、`continue-on-error`。

## 結束時
1. 在指定的分支上 commit 並 push，不得動 main。
2. 把結果寫到 `docs/reports/O-028.md`：完成摘要、變更檔案、測試結果、未完成事項、需要人類決定的問題。不要自行量 CI 分鐘數。
3. 測試結果、權限被拒以 workflow 自動產生的摘要與 PR 觸發的 CI run 為準，報告不重貼。

## SRE 接線（Claude Code 不做；Claude 的 run 成功後由 SRE 在同一分支加 commit）
- `ci-guard-mode.sh`：`task/**`、`fix/**` push 時，用 `BEFORE_SHA..SHA` 算 `--qa-changed`；`BEFORE_SHA` 為空、全 0（新分支）、不在 clone、不是 `SHA` 的祖先（force push）、diff 失敗 → `--qa-changed-error`。依「前一次推送」規則呼叫 activity API 取 `--prev-qa-changed`，判不出來 → `--prev-skip`。驗證段落允許「light＋`tests-only-no-pr`＋PR 編號空」，輸出 `mode_reason`、`qa_batch_warning`；後者為 true 時印 `::warning title=QA 補充測試請合併推送::…`，不影響 exit code。
- `ci.yml`：ci-guard 新增上述兩個 output，`ci-ok` 的 Decide 步驟多傳 `MODE_REASON`。不新增 ci.yml 的 job、不調高逾時、不改 `pull_request` 觸發。
- `ci-supersede.yml`：`on: workflow_run`（workflows: `ci`，types: `completed`）；job 層 `if` 只在「同 repo，且（push run 為 failure，或為 pull_request run）」時跑；頂層 `concurrency` 依 head SHA、不取消；`timeout-minutes` 5；權限見 AC-O28-9；步驟只呼叫 `ci-supersede.sh`（gh api 讀 runs、jobs、statuses，交給 `tooling/ci-supersede.mjs`，依結果 `POST statuses`；`target_url` 用 PR run 的網頁連結）。gh 失敗即非 0。
- `ci-workflow-check.mjs`：凍結 AC-O28-9（觸發、權限、無 `ref`、`persist-credentials: false`、context 名稱）；`ci-budget.json` 同步。
- 開 [G3] PR 時「Actions 分鐘數影響」寫實際估算：ci.yml 每次被降 light 的 push 省下 `check`／`taskcheck`；`ci-supersede.yml` 每次符合條件的 ci 完成多 1 個短 job。

## 停止並回報
- 同一失敗原因連續 2 次 CI 紅燈：停止修改，帶原始日誌與 run 連結回報幕僚長。
- 發現必須改產品程式、改必過檢查、新增 ci.yml 的 job 或調高逾時才能完成：停下，不要自行擴大範圍。

## 不確定
- activity API 的欄位（`before`、`after`、`activity_type`）以 GitHub REST 文件為準；本單測試用 fixture。SRE 接線時以本 repo 實際回應確認一次，若欄位不同，停下回報，不改規則。
- `workflow_run` 只在 workflow 檔進預設分支後才會觸發；`ci-supersede.yml` 的實際行為要等 G3 合併後，下一次自然發生「push 紅、PR 綠」時確認，不為測試故意製造紅燈。
