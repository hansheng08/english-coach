## 設計決定
- **`RouteDeps` 多一個必填 `log`**：§4.19 要求 `recordCall` 失敗時 log 一行 `tts recordCall kind=<kind>`，`RouteDeps` 原本沒有 log 入口。已在同一個 commit 補 `makeTestRouteDeps` 預設值與 `index.ts` 接線。請 Architect 確認。
- **`UserClient` 多一個 `tts` 欄位**（`TtsDbClient`）：`DbClient` 與 `ReviewDbClient` 的 `from` 形狀不同，疊在一起無法同時 `insert` 與 `select`，所以另開欄位（`client.ts` 只放寬回傳型別）。
- **用量過渡**：`sumPaidUsageThisMonthNtd` 不在 main，`resolve('tts', …)` 第三個參數暫傳 `0`（`api/tts.ts` 唯一呼叫點），由 T-020 的用量接線改接；TASKS 備註請 TechLead 補。
- **`tts` 回傳型別 `TtsOutcome`**：QA 探針 `api-client-factory.qa.test.ts` 以 `ApiClient & { tts(): Promise<{ ok; error? }> }` 呼叫後直接讀 `r.error`。交集重載取第一個簽名，嚴格的 `Result` 會讓 `tsc -b` 失敗，而 QA 檔不能改。所以回傳型別是 `Result<TtsResponse, AppError> & { error?: AppError }`（執行時行為不變）。T-020 把 `tts` 改回必填、QA 改探針後可收回這個型別。
- **`createSupabaseApiClient(auth, deps?, config?)`**：`deps` 有預設值（全域 `fetch`、`getAccessToken` 回 `null`），因為既有測試與 QA 探針仍只傳 `auth`。`createApi` 一定注入 `fetch`、`getAccessToken`、`functionsUrl`、`publishableKey` 與 `tts` bucket。`functionsUrl` 沒設時預設本機 `http://127.0.0.1:54321/functions/v1/api`（QA-17 要求絕對網址）。
- **伺服器錯誤 → `AppError`**：`/tts` 不會回的種類（`not_found`、`conflict`、`news_unavailable`）統一成 `internal`；`storage_failed` 的 `op` 取 `download`（錯誤本文沒帶 `op`）。
- **播放器**：同一個 `<audio>` 重複使用；`repeat` 對每個來源各套一次；`resolve` 一個來源只呼叫一次。
- **`mp3DurationMs`** 放在 `_shared/tts/cache.ts`，Azure adapter 沒改（公式相同）。
- **`TtsSettingsSchema`** 由本單建在 `settings.ts`（T-020 的 `SettingsSchema` 尚未在 main）。
- `tts.wav` 是 864 位元組、約 0.1 秒的靜音 PCM（用 `printf` 產生，Write 工具寫不了 NUL）。
